# Qualification Knowledge-Construction Pipeline

**Status:** governed architecture, implementation-complete for the generic pipeline stage this document covers (candidate generation + gap/conflict analysis). Package: `@alp/qualification-pipeline` (`packages/qualification-pipeline/src/`). This document is the design authority; the package is its operational encoding, proved by the synthetic regression suite in `packages/qualification-pipeline/src/rules.test.ts`.

**Scope of this package:** raw qualification evidence → normalized/validated evidence → learner-performance/knowledge **candidates** → **gap/conflict analysis**. It stops there. It never writes a governed course matrix, knowledge obligation, assertion, or lesson — see §17 (Downstream Gate).

**Independence:** this package has zero dependency on any other workspace package and contains no qualification-specific content or branching. Every example in this document is illustrative; none of the terms used here (or in the package's own test fixtures) may appear as a literal in the package's production source (`types.ts`, `rules.ts`, `index.ts`) — mechanically enforced by a dedicated test.

**Revision history:**
- **CC-18** established the generic pipeline: source-role hierarchy, assessment as a proposition-generation source, AC-vs-Range scope, exemplar/mastery separation, technical-truth/curriculum-scope separation, structured gaps.

- **CC-18B** closes a second round: the pipeline is locked to one qualification per run; the official-unit registry is keyed compositely and conflict-checked; curriculum evidence is itself validated against that registry (not just assessment); the ambiguous boolean pair driving curriculum-candidate creation is replaced by a locked, explicit normalization kind that lets Range members create their own candidates; candidate generation groups by the full `(subject, performanceType)` key so multiple performance types per subject all survive; assessment evidence is validated into a single trusted stream that every downstream consumer must use exclusively; `normalizationBasis` is checked for type-compatibility per evidence type; capability dependencies become an independent, provenance-bearing relation instead of a self-declared curriculum field; technical-truth coverage becomes claim-key-exact instead of subject-matched; factual-claim comparison requires compatible comparison kinds; exemplars carry mandatory provenance and no longer auto-gain technical-truth confidence from their own role; category/family relationships are validated against the qualification and the set of subjects actually present in normalized evidence.
- **CC-18C** closed five remaining implementation-integrity defects at the same boundary, none of which changed the pipeline's design: (1) a normalization proposal that fails provenance validation is now **always** reported as `EVIDENCE_NORMALIZATION_REVIEW`, naming the exact failure — CC-18B still silently dropped a basic blank-`sourceRef`/`sourceLocator` failure in several validating functions and in the `OfficialCurriculumUnit` registry itself, reporting a gap only for the separate, narrower case of a type-incompatible-but-present `normalizationBasis`; (2) `CandidateCapabilityRequirement` is bound to the active `qualificationId`, and `EXPLICIT_CURRICULUM_OPERATION`/`EXPLICIT_ASSESSMENT_OPERATION` derivations must cite a role-**and**-id-matched entry in the correspondingly validated curriculum/assessment stream, closing a loophole where an `EvidenceRef` reusing a real `evidenceId` under the wrong role could satisfy the gate; (3) `DETERMINISTIC_OPERATIONAL_DEPENDENCY` is downgraded from an auto-promoting `derivationKind` to a deliberate, documented HOLD (§11.2) — it let an upstream adapter self-authorise a prerequisite by enum choice alone, with no governed deterministic-rule registry backing it; (4) `CandidateFactRequirement.qualificationId` becomes mandatory and the type gains a locked `derivationStatus` mirroring the capability-requirement citation pattern, plus its own dedicated `normalizationBasis` (`FACT_REQUIREMENT_DERIVATION`) so a technical source can never be misread as authorising what the course requires (§16.1); (5) multiple `TECHNICAL_TRUTH` claims for the same `(subject, claimKey)` are now resolved deterministically rather than by first-array-match, with a new `TECHNICAL_TRUTH_CONFLICT_REVIEW` gap type for claims that disagree among themselves (§16.2); and depth qualifiers gain an explicit `refinesPerformanceType` target so a `DEPTH_QUALIFIER` can never be misapplied across every performance type sharing a subject (§6.1).
- **CC-20** adds a new, explicit **semantic adjudication** stage in response to findings from a completed blind back-test: (A) deterministic specification→scope extraction works well; (B) technical truth must remain unable to create curriculum scope; (C) auto-accepting every technically valid inferred fact overteaches; (D) auto-rejecting every non-literal fact is too conservative; (E) absence of assessment evidence cannot automatically mean `depthConfidence: NONE` for every candidate; (F) a leaf/mastery candidate with zero governing fact requirements must not read as though technical knowledge is simply "not required." CC-20 addresses these with four additions, none of which are qualification-specific rules or subject-string branches: a governed `SemanticAdjudication` decision record over already-existing fact proposals (§21); an explicit candidate-level `KnowledgeBoundaryStatus` and a corrected `TechnicalCoverageStatus` that can no longer render "never examined" identically to "structurally not applicable" (§22); a `DepthBasis` model in which qualification-level evidence supplies a genuine (if weaker) depth ceiling instead of leaving every un-assessed candidate at `depthConfidence: NONE` (§23); and a `KNOWLEDGE_DECOMPOSITION_GAP` gap type that closes the exact false-green case finding F names.

- **CC-20B** is a further narrow correction closing two remaining semantic-integrity gaps and one audit gap in CC-20A's implementation, again found before any real-qualification use: (1) `OVERDEPTH_FORMALISM` previously accepted "any real evidence match", including `TECHNICAL_TRUTH` alone — too weak, since a factual authority can prove a proposition true without ever proving the qualification excludes it as beyond required depth; it now requires real qualification/depth authority (curriculum + qualification-level, assessment-mapped depth evidence, or a candidate's own already-governed explicit curriculum depth qualifier) — §21.6; (2) `PerformanceProvenance.EXPLICIT` previously meant only "a normalized `commandVerbPerformanceType`/`performanceType` enum is populated" — insufficient, since a populated enum is normalization OUTPUT, not itself source evidence, and a normalizer's own strong inference could reach `EXPLICIT` merely by filling the field in; a new `PerformanceEvidenceBasis` (`SOURCE_EXPLICIT`/`STRONG_INFERENCE`) now gates it, and governed inheritance can never upgrade an inferred parent into explicit/governed depth — §23.1; (3) the CC-20A evidence-support gate applied only to GOVERNING adjudications, silently exempting invalid non-governing ones (`CONTEXT_ONLY`/`REJECT_*`/`REPRESENTATIVE_EXEMPLAR`/`UNRESOLVED`) from any check at all — every adjudication, governing or not, is now gated identically, auditable on rejection, and has zero semantic effect when rejected — §21.6.
- **CC-21B** is a narrow, inspect-first correction to CC-21A: verification found that a `COMPLETE` `KnowledgeBoundaryCertification` could bypass an unresolved candidate-level knowledge decomposition for a non-structural, mastery-bearing candidate with zero governing `requiredFactKeys` and zero governed child decomposition, provided it had once been examined by an adjudication that resolved to nothing governing (e.g. every proposal was `CONTEXT_ONLY`/`REJECT_*`) — a real, if narrow, hole distinct from CC-21A's own false-green (§22.1, §22.4). Curriculum evidence proves a performance is required; it never proves that an empty learner-knowledge boundary is complete. `finalizeKnowledgeBoundary` now requires an **adequate constructed boundary** (at least one governing `requiredFactKey`, since genuine structural exhaustion by governed children is detected and returned entirely by the earlier `STRUCTURALLY_DECOMPOSED` branch and never reaches this check) before a `COMPLETE` certification is honoured for a non-structural candidate; an incompatible `COMPLETE` certification is rejected with its own `KNOWLEDGE_BOUNDARY_CERTIFICATION_GAP`, never silently discarded, and the candidate's status is unaffected by its presence. The already-safe "never examined at all" case (CC-20 finding F) needed no behaviour change. No Unit-202 content, back-test artefact, or qualification-specific literal is touched.

This package's own `StandardPipelineResult` (candidates + gaps + certifications) is unchanged by CC-23 — CC-23 only extends the documented pipeline (§25) with what happens to an APPROVED knowledge boundary next, and this package remains the sole authority for producing that boundary. See §25 for the new stages and ADR-0007 for the package-boundary decision.
- **CC-23A** (this revision) is a Project-Architect-directed hardening of CC-23's own generic architecture, not a redesign: (1) `canonicalRequirementKey` moves from normalized DISPLAY TEXT to `KnowledgeTarget.semanticIdentity` (mandatory `{semanticNamespace, semanticKey}`) — closing a real homonym-collision risk display-text-based reuse could never safely rule out (§25.5); (2) `SourceAuthorityClass` becomes an open, extensible string type with domain-neutral standard defaults, rather than a closed enum requiring a code change per new domain (§25.5); (3) the end-to-end pipeline diagram (§19) is corrected so `COURSE-CONSTRUCTION HANDOFF` names exactly one stage, at the very end, after technical evidence, assertion construction, and a new explicit `COVERAGE GATE` stage — never this package's own interim `StandardPipelineResult` milestone (renamed `QUALIFICATION-PIPELINE OUTPUT` to remove the ambiguity). CC-23A also adds a generic formula+rearrangement decomposition rule (§25.4 class E2) and a generic directional/operational-rule metadata field (`directionalMapping`), and uses both, plus the new semantic-identity model, to resolve all 8 of CC-23's own Unit-202 preflight `SEMANTIC_DECOMPOSITION_REQUIRED` gaps through the generic mechanisms alone — zero Unit-202-specific planner code. See §25.11-§25.13 and ADR-0007's ratification note.
- **CC-21A** closes a false-green discovered by semantic review of the CC-21 rerun: `knowledgeBoundaryStatus: GOVERNED` was reachable purely because a candidate's governing facts had all mechanically resolved (every `requiredFactKey` traced to a real proposal/adjudication, `technicalCoverageStatus: COMPLETE`) — treating "every currently-known requirement happens to be satisfied" as equivalent to "the resulting knowledge boundary is semantically sufficient," which are different questions (§22.1, §22.4). CC-21A introduces `KnowledgeBoundaryCertification`, a governed **semantic certification** over an existing candidate's already-constructed knowledge state — never a new evidence/scope source, never able to create a candidate, fact, claimKey, or requirement of its own (§22.4). `GOVERNED` is now reachable **only** through a certification whose `decision` is `COMPLETE`, whose `boundaryFingerprint` exactly matches the pipeline's own currently-computed fingerprint for that candidate's fact/adjudication/performance/child-decomposition state (a stale certification never survives a changed boundary automatically), and whose `supportingEvidenceRefs` resolve to real `OFFICIAL_CURRICULUM`/`PUBLIC_ASSESSMENT` authority for the exact candidate (`TECHNICAL_TRUTH` alone can prove a fact true but can never certify a boundary complete). Absence of a valid certification now produces `ADJUDICATION_REQUIRED` plus a new `KNOWLEDGE_BOUNDARY_CERTIFICATION_GAP`, never a silent pass. Two new gap types (`KNOWLEDGE_BOUNDARY_CERTIFICATION_GAP`, `KNOWLEDGE_BOUNDARY_CERTIFICATION_CONFLICT`) make every rejection and every conflicting certification pair auditable. This package-level change touches no qualification-specific content: Unit 202's frozen clean-room evidence and back-test artefacts are untouched, and no Unit-202-specific certification exists anywhere in this revision.

## 1. Why this exists

CC-17's Unit 202 blind-calibration experiment proved the underlying idea — a course can be constructed from transferable evidence, without proprietary course-provider material. CC-18/18A hardened the *generic* pipeline's rules. CC-18B hardens the boundary one layer earlier: the raw-source → normalized-evidence step itself. A pipeline can apply every rule correctly and still be too trusting if a single fixture, or a future qualification-specific adapter, can hand-author a relationship (a bare mapped-unit string, an arbitrary category label, a self-declared necessity, a pre-labelled conflict) that the pipeline then treats as proven. Every mechanism in this document exists to make that impossible before the real Unit 202 blind back-test.

## 2. Source-role hierarchy (locked)

Seven evidence roles, each with exactly one role in the pipeline. This hierarchy is a locked product decision this package implements, not something it revises.

| Role | Representative type(s) | Pipeline role |
|---|---|---|
| `OFFICIAL_CURRICULUM` | `CurriculumEvidence`, `OfficialCurriculumUnit` (registry), `CurriculumSubjectRelation`, `CurriculumFamily` | Curriculum **scope** authority |
| `PUBLIC_ASSESSMENT` | `AssessmentEvidence` | Learner-performance discovery + depth/performance calibration |
| `QUALIFICATION_LEVEL` | `QualificationLevelEvidence` | Depth constraint only — **never** scope-creating |
| `TECHNICAL_TRUTH` | `SourceFactualClaim` (`sourceRole: TECHNICAL_TRUTH`) | Factual truth only — **never** curriculum-scope authority on its own |
| `OPTIONAL_CALIBRATION` | `OptionalCalibrationEvidence`, `SourceFactualClaim` (`sourceRole: OPTIONAL_CALIBRATION`, diagnostic use only) | Optional external calibration benchmark — **never** required by the standard pipeline |
| `LEGACY_DIAGNOSTIC` | `LegacyDiagnosticEvidence` | Diagnostic/comparison only — never scope, depth, or factual authority |
| `MODEL_KNOWLEDGE` | *(no evidence type — never a valid input)* | No evidential authority |

`STANDARD_MODE_CANDIDATE_ROLES` are the only roles `buildStandardPipeline` will accept for role-tagged evidence. `DIAGNOSTIC_ONLY_ROLES` can never reach a required candidate in standard mode (§13). `PrerequisiteEvidence` (`kind: "STRUCTURAL_PREREQUISITE_DEPENDENCY"`) and `CandidateCapabilityRequirement` are deliberately **not** tagged with one of the 7 roles — they are derived structural relations, not primary evidence sources.

## 3. The active qualification boundary

Every `StandardPipelineInput` carries exactly one `qualificationId`. A run only ever concludes scope for that qualification. Every qualification-specific evidence type carries its own `qualificationId` (`CurriculumEvidence`, `AssessmentEvidence`, `CurriculumSubjectRelation`, `CurriculumFamily`, `QualificationLevelEvidence`, `OfficialCurriculumUnit` in the registry, and — as of CC-18C — `CandidateCapabilityRequirement` and the now-mandatory `CandidateFactRequirement.qualificationId`) and is validated or filtered against the active run's `qualificationId` — never merely relied upon as a pre-filtered caller convention. `CurriculumEvidence`/`AssessmentEvidence` failing this check are excluded and reported (`CURRICULUM_MAPPING_REVIEW` / `ASSESSMENT_MAPPING_REVIEW`); `CandidateCapabilityRequirement`/`CandidateFactRequirement` from another qualification are excluded and reported (`EVIDENCE_NORMALIZATION_REVIEW`, CC-18C — a foreign-qualification requirement can neither auto-promote a prerequisite (§11) nor contribute a `requiredFactKey` (§16.1)); `CurriculumSubjectRelation`/`CurriculumFamily`/`QualificationLevelEvidence` from another qualification are silently filtered (they are structural registries, not scope-generating evidence, so a mismatch is not itself reportable scope loss).

## 4. Official curriculum-unit registry — composite identity

`OfficialCurriculumUnit { curriculumUnitId, qualificationId, sourceRef, sourceLocator, officialWording, learningOutcomeId?, parentCurriculumUnitId? }` is never itself a candidate list — it is the real, authoritative set of AC/LO/curriculum units available for mapping.

`buildOfficialCurriculumUnitIndex` keys it by the **composite** `unitRegistryKey(qualificationId, curriculumUnitId)`, never `curriculumUnitId` alone — two different qualifications may legitimately share the same bare unit id (e.g. both naming an "AC1.1"), and each must resolve independently. Registry insertion order never affects the result: entries are grouped by composite key regardless of array order, so the outcome for a given qualification+unit pair is identical no matter how the registry array was assembled.

A genuine registry conflict — the same composite key appearing more than once with **incompatible** `officialWording` or `sourceRef` — excludes **both** duplicates from the resolvable index and is reported as an `EVIDENCE_NORMALIZATION_REVIEW` gap, never resolved last-write-wins. Two entries sharing a composite key that genuinely agree are not a conflict.

**CC-18C:** `OfficialCurriculumUnit` does not itself extend the `SourceProvenance` shape (it carries no `normalizationBasis` — it *is* mapping authority, not a normalization proposal against one), but it still carries mandatory `sourceRef`/`sourceLocator`. `buildOfficialCurriculumUnitIndex` rejects and reports (`EVIDENCE_NORMALIZATION_REVIEW`) any unit with a blank `sourceRef` or `sourceLocator` before it is even considered for the index — a blank-provenance entry can never become mapping authority, and every `CurriculumEvidence`/`AssessmentEvidence` record attempting to resolve against it is correctly rejected downstream via `CURRICULUM_MAPPING_REVIEW`/`ASSESSMENT_MAPPING_REVIEW`, with both gaps visible.

## 5. Curriculum evidence validation

CC-18A validated only assessment mappings against the registry. CC-18B validates `CurriculumEvidence` itself, via `validateCurriculumEvidence`, before any candidate is generated from it. A record is accepted only when **all** of:

- **A.** its `qualificationId` matches the active pipeline `qualificationId`;
- **B.** its `curriculumUnitId` resolves to a real `OfficialCurriculumUnit` under the composite key;
- **C.** its source provenance is valid (§14);
- **D.** its `normalizationBasis` is type-compatible for curriculum evidence (`EXPLICIT_CURRICULUM_WORDING` or `EXPLICIT_RANGE_STRUCTURE`) — an incompatible basis produces `EVIDENCE_NORMALIZATION_REVIEW` rather than being silently accepted or silently dropped;
- **E.** its `role` is `OFFICIAL_CURRICULUM` (structurally guaranteed by the type; re-checked at runtime as defense in depth).

A fabricated `curriculumUnitId`, or a record belonging to another qualification, never generates required scope — it is preserved as a `CURRICULUM_MAPPING_REVIEW` gap naming the attempted mapping and the exact reason it was not trusted.

## 6. Curriculum normalization kind — replacing the ambiguous boolean pair

CC-18/18A's `namedInPrimaryWording`/`isRangeItem` boolean pair let any provenance-valid record with neither flag set (a genuine bug) still generate required scope. It is replaced by an explicit, **locked** `CurriculumNormalizationKind`, declared by the normalization record itself — never inferred from the subject's own English word in production logic:

- **`PRIMARY_REQUIREMENT`** — text explicitly appears as required AC/LO/criterion wording. Creates `REQUIRED_EXPLICIT_CURRICULUM`.
- **`RANGE_REQUIRED_MEMBER`** — an explicit Range member a learner may be required to distinguish/identify/apply. Creates its **own** `REQUIRED_EXPLICIT_CURRICULUM` candidate (`requiresSubject` is required for this kind and is preserved on the resulting candidate as `parentSubject`) — CC-18/18A's `refinesSubject` mechanism silently treated every Range member as depth-only, which this corrects.
- **`RANGE_CATEGORY`** — a named broad Range category. Creates the category requirement; may carry `breadthStatus` (§9).
- **`DEPTH_QUALIFIER`** — official wording that constrains/deepens an existing required subject but does not independently represent learner content. Creates **no** independent candidate; only raises the depth confidence of the **exact** `(subject, performanceType)` candidate it targets.

### 6.1 Range members must not disappear

The canonical regression: a primary subject with three official Range members (e.g. three named classes) produces **four** required candidates — the parent plus each member, each independently `REQUIRED_EXPLICIT_CURRICULUM`, with the parent/child relationship preserved via `parentSubject`, never silently collapsed into "the parent alone, with the members as bare depth colour." A genuine depth qualifier (constrains without representing independent content) is still expressible via `DEPTH_QUALIFIER` and remains non-candidate — the explicit kind controls which behaviour applies, never a guess.

### 6.2 Depth qualifiers must be performance-specific (CC-18C)

Candidate identity is `(subject, performanceType)`, never subject alone. CC-18B's `DEPTH_QUALIFIER` raised depth confidence for its `refinesSubject` alone — correct when that subject carried exactly one performance-type candidate, but silently wrong (applying broadly to every performance type sharing the subject) the moment it carried more than one. `CurriculumEvidence.refinesPerformanceType` closes this: when present, the qualifier resolves to exactly the `(refinesSubject, refinesPerformanceType)` candidate and no other. When omitted, `generateCurriculumCandidates` resolves it only if `refinesSubject` has exactly one performance-type candidate of its own; if the subject carries more than one and no explicit target was supplied, the qualifier cannot resolve to a single intended candidate and is **never** applied broadly — it is excluded and reported as `EVIDENCE_NORMALIZATION_REVIEW` instead. Regression: a subject with both `IDENTIFY` and `CALCULATE` candidates, and a depth qualifier explicitly targeting `CALCULATE`, raises `CALCULATE`'s depth confidence only and leaves `IDENTIFY` at `NONE`; the same qualifier with no explicit target resolves to neither and is reported for review.

## 7. Multi-performance-type preservation

Candidate identity remains `(subject, performanceType)`. CC-18/18A's curriculum-candidate generation grouped records by subject FIRST and then picked a single command-verb performance type, silently discarding the others if the same subject appeared under multiple official requirements with different verbs. `generateCurriculumCandidates` now groups by the full `(subject, performanceType)` key from the start: three official requirements sharing a subject under `IDENTIFY`/`DESCRIBE`/`CALCULATE` survive as three independent candidates. Source order never changes which performance types survive.

## 8. Validated assessment stream

`validateAssessmentEvidence` produces the single trusted `validated` stream — provenance-valid, type-compatible `normalizationBasis`, resolved against the registry under the active qualification. **Every** downstream function that treats assessment as evidence — `generateAssessmentCandidates`, `detectAssessmentPatternCandidates`, `computeCategoryBreadthOutcomes`, and `EXPLICIT_ASSESSMENT_OPERATION` capability-dependency substantiation (§11) — consumes **only** this validated stream, never the raw input array. `generateAssessmentCandidates` itself now contains no validation logic at all; it trusts its input completely because validation is a separate, prior step.

### 8.1 Rejection propagates

Two assessment items sharing a governed `familyKey`, one validly mapped and one mapped to a fabricated unit: the invalid one produces `ASSESSMENT_MAPPING_REVIEW` and is entirely absent from the validated stream, so it cannot count toward the two-distinct-member threshold a family pattern requires (§10) and cannot appear in a `SCOPE_BREADTH_GAP`'s evidenced sub-items (§9.1) — an invalid item influences nothing downstream, by construction, not by a second round of filtering at each call site.

## 9. Category breadth status — independent of assessment presence

`CurriculumEvidence.breadthStatus` (meaningful only on `RANGE_CATEGORY` records) is declared explicitly by curriculum normalization — never guessed from the category's own English word. Undeclared defaults to `UNKNOWN`, never silently complete.

- **`ENUMERATED_COMPLETE`** — no scope-breadth gap is ever produced, regardless of assessment coverage.
- **`OPEN_OR_UNDERSPECIFIED`** — a `SCOPE_BREADTH_GAP` (and a companion `OPEN_SCOPE_GAP` candidate, `candidateKey: "{subject}::unresolved-breadth"`) is produced **unconditionally**, with or without any assessment evidence at all — required for the degraded-evidence back-test this package exists to support.
- **`UNKNOWN`** — a `REVIEW_REQUIRED` candidate (kept structurally distinct from `OPEN_SCOPE_GAP` so a reviewer can tell "known-broad" from "breadth status itself never declared") plus a `SCOPE_BREADTH_GAP` naming that the breadth status itself is unresolved.

### 9.1 Governed sub-item evidence

An `AssessmentEvidence.underCategory` label only counts toward a breadth gap's evidenced sub-items when a matching, governed `CurriculumSubjectRelation { qualificationId, subject, underCategory, ...provenance }` also exists (§12), drawn from the validated assessment stream only (§8.1).

## 10. Assessment family-pattern generalisation

`AssessmentEvidence.familyKey` only counts when it resolves to a governed `CurriculumFamily { qualificationId, familyKey, memberSubjects, ...provenance }` that lists the item's own `subject` as a member (§12). A pattern candidate (`disposition: REVIEW_REQUIRED`) is emitted only when the same performance type is evidenced, from the validated stream, across at least two distinct, governed member subjects. A single tested member never generalises, an ungoverned family label never generalises no matter how many distinct subjects share it, and an invalid assessment item can never count toward the threshold (§8.1).

## 11. Structural capability dependency — independent of curriculum scope records

CC-18A let `CurriculumEvidence.requiredCapabilityKeys` self-declare what a required performance needs, and a `PrerequisiteEvidence.necessityKind` self-declare its own necessity. Both self-authorisation points are removed.

`CandidateCapabilityRequirement { qualificationId, targetSubject, targetCandidateKey, capabilityKey, derivationKind, sourceEvidenceRefs, ...provenance }` is an **independent**, provenance-bearing relation declaring that a required candidate structurally needs a capability. **CC-18C:** it is validated (`validateCandidateCapabilityRequirements`) against provenance (§14, always reported on failure) and the active `qualificationId` before anything downstream sees it — a requirement declared for a different qualification is filtered out and reported, and can never influence this run's prerequisite promotion, even if its `targetCandidateKey` happens to collide with a real candidate. `derivationKind` is locked:

- **`EXPLICIT_CURRICULUM_OPERATION`** — may auto-promote, but only when at least one `sourceEvidenceRefs` entry has `role: OFFICIAL_CURRICULUM` **and** its `evidenceId` resolves into the validated curriculum stream (§5) for this run.
- **`EXPLICIT_ASSESSMENT_OPERATION`** — may auto-promote, but only when at least one `sourceEvidenceRefs` entry has `role: PUBLIC_ASSESSMENT` **and** its `evidenceId` resolves into the validated assessment stream (§8) for this run. An `EvidenceRef` that merely reuses a real, validated `evidenceId` under the **wrong** role (e.g. a validated assessment item's id cited with `role: OFFICIAL_CURRICULUM`) never satisfies this gate (CC-18C closes this collision loophole) — the citation must match on role **and** id together.
- **`DETERMINISTIC_OPERATIONAL_DEPENDENCY`** — never auto-promotes; see §11.2.
- **`REVIEW_PROPOSED`** — never auto-promotes. A raw claim that "this subject probably requires skill X" is `REVIEW_PROPOSED`, not an automatic prerequisite.

A `PrerequisiteEvidence` proposal (`capabilityKey`, `necessaryForCandidateKey`, `minimalDepthJustification`) becomes `FOUNDATIONAL_PREREQUISITE` only when a validly-provenanced, correctly-qualification-bound `CandidateCapabilityRequirement` exists for the same `(targetCandidateKey, capabilityKey)` pair with an auto-promoting `derivationKind` and a satisfied citation. Two weaker, deterministic outcomes:

- a real required target exists but no matching capability requirement auto-promotes (`REVIEW_PROPOSED`, `DETERMINISTIC_OPERATIONAL_DEPENDENCY`, an unsatisfied citation, or none found at all) → `REVIEW_REQUIRED`;
- no real required target exists → `CONTEXTUAL_TEACHING_SUPPORT`.

### 11.1 Assessment-derived dependencies must use validated items

A `CandidateCapabilityRequirement` with `derivationKind: EXPLICIT_ASSESSMENT_OPERATION` auto-promotes only when at least one of its `sourceEvidenceRefs` names an assessment item present in the validated stream (§8) **under the matching role** (see above). A dependency derived from a rejected or unmapped assessment item can never auto-promote a prerequisite.

### 11.2 `DETERMINISTIC_OPERATIONAL_DEPENDENCY` — deliberate HOLD (CC-18C)

`DETERMINISTIC_OPERATIONAL_DEPENDENCY` exists in the locked `derivationKind` enum to name a real category of dependency — one that follows deterministically from the structure of an operation (e.g. "you cannot perform this calculation without this prerequisite arithmetic skill") rather than from an explicit curriculum/assessment citation. CC-18B let it auto-promote on the strength of the enum choice alone, with no governed registry backing *which* deterministic rules are actually authorised — this let an upstream normalization adapter self-authorise a prerequisite simply by picking this `derivationKind` over `REVIEW_PROPOSED`.

As of CC-18C, `DETERMINISTIC_OPERATIONAL_DEPENDENCY` **never** auto-promotes — `isAutoPromotable` returns `false` for it unconditionally, identically to `REVIEW_PROPOSED`, regardless of how well-cited its `sourceEvidenceRefs` are. This is a deliberate, temporary HOLD, not a design conclusion: a future package may define a governed deterministic-dependency-rule registry (analogous to the `OfficialCurriculumUnit` registry) against which such a claim could be validated before auto-promoting. Designing that registry is explicitly **out of scope** for CC-18C and is not implied by this HOLD — until it exists and is separately authorised, automatic prerequisite promotion is limited to properly source-cited `EXPLICIT_CURRICULUM_OPERATION` and `EXPLICIT_ASSESSMENT_OPERATION`.

## 12. Governed category/family relationship validation

`CurriculumSubjectRelation` and `CurriculumFamily` are validated (`validateCurriculumSubjectRelations`, `validateCurriculumFamilies`) against three things before being trusted at all:

1. they belong to the active qualification;
2. their `normalizationBasis` is type-compatible (`EXPLICIT_CURRICULUM_WORDING` or `EXPLICIT_RANGE_STRUCTURE`);
3. every subject they reference (a relation's `subject` and `underCategory`; a family's every `memberSubjects` entry) is present in the set of subjects **known** to the run — subjects appearing in validated curriculum evidence *or* the validated assessment stream (§8), so a relation can legitimately connect a category to a subject that assessment evidence itself validly reveals, while a subject with no supporting evidence anywhere is rejected.

An arbitrary relation or family object with non-empty strings is never governed merely because it was supplied — a relation referencing an unknown subject, or a family listing even one unknown member, is rejected wholesale and reported as `EVIDENCE_NORMALIZATION_REVIEW`.

**Confirmed governed boundary (CC-18C, no behaviour change):** "known" in point 3 above is deliberately **curriculum + validated-assessment-derived** subjects, not curriculum-only — a relation may legitimately connect a category to a subject that only assessment evidence validly reveals, which is the correct behaviour for a family/relation record authored *after* seeing what assessment evidence turned up. This is CC-18B's original implementation, carried forward unchanged; it is stated explicitly here because CC-18C's own review found the surrounding prose could be misread as curriculum-only, which it never was.

## 13. Standard-mode exclusion of optional-calibration and legacy content

`buildStandardPipeline`'s own input type does not accept `OptionalCalibrationEvidence` or `LegacyDiagnosticEvidence`, and rejects at runtime any role-tagged evidence whose own `role`/`sourceRole` is not one of the standard-mode roles — including a `SourceFactualClaim` with `sourceRole: OPTIONAL_CALIBRATION` passed via `factualClaims`, which only `OFFICIAL_CURRICULUM`/`TECHNICAL_TRUTH` claims may populate.

The only legitimate uses of calibration/legacy evidence are read-only, called only *after* the standard pipeline has produced its candidates, and never merged back into `StandardPipelineResult`: `compareAgainstDiagnosticEvidence` (subject-level comparison) and `compareCalibrationFactualClaims` (claim-key factual comparison against approved technical truth, §16).

## 14. Source-normalization provenance

Every evidence record capable of influencing required scope, learner performance, depth, prerequisite status, category/family relationship, or factual truth (`CurriculumEvidence`, `AssessmentEvidence`, `QualificationLevelEvidence`, `PrerequisiteEvidence`, `CandidateCapabilityRequirement`, `ExemplarEvidence`, `CurriculumSubjectRelation`, `CurriculumFamily`, `SourceFactualClaim`, `CandidateFactRequirement`) carries mandatory, non-optional `sourceRef`, `sourceLocator`, and a `normalizationBasis` drawn from a governed enum. `hasValidProvenance(evidence, allowedBases?)` is the runtime gate every validating/generating function applies — non-empty `sourceRef`/`sourceLocator` after trimming, a real `normalizationBasis` enum member, and (when an `allowedBases` list is supplied) type-compatibility with the specific evidence type carrying it. A record failing any of these checks is excluded from candidate generation.

**CC-18C — no rejection is ever silent.** CC-18B already reported a basic-but-type-incompatible `normalizationBasis` as `EVIDENCE_NORMALIZATION_REVIEW`, but several validating functions still handled a more basic failure (blank `sourceRef`/`sourceLocator`, or an unrecognised `normalizationBasis` entirely) with a bare `if (!hasValidProvenance(e)) continue;` — the proposal simply vanished, with no gap naming what was attempted or why it failed. This violated the three-layer anti-cheating contract (§19.1): layer C (pipeline acceptance/rejection **and reason**) must never be skipped. Every validating function in this package now uses a single, uniform check (`provenanceFailureReason`, returning the exact human-readable failure — `"sourceRef is empty"`, `"sourceLocator is empty"`, or a `normalizationBasis` message) that **always** produces an `EVIDENCE_NORMALIZATION_REVIEW` gap on failure, for every evidence type listed above plus the `OfficialCurriculumUnit` registry itself (§4) — never a silent `continue`. The gap preserves the proposal's own evidence id, evidence type, `sourceRef`, `sourceLocator`, and `normalizationBasis` exactly as supplied, so a rejected proposal remains fully traceable for review rather than disappearing.

Allowed bases per evidence type: `CurriculumEvidence` → `EXPLICIT_CURRICULUM_WORDING`/`EXPLICIT_RANGE_STRUCTURE`; `AssessmentEvidence` → `POSITIVE_ASSESSMENT_TARGET`/`ASSESSMENT_CURRICULUM_MAPPING`; `QualificationLevelEvidence` → `QUALIFICATION_LEVEL_DESCRIPTOR`; `PrerequisiteEvidence` → `STRUCTURAL_PREREQUISITE_DEPENDENCY`; `CandidateCapabilityRequirement` → `CAPABILITY_DEPENDENCY_DERIVATION`; `CurriculumSubjectRelation`/`CurriculumFamily` → `EXPLICIT_CURRICULUM_WORDING`/`EXPLICIT_RANGE_STRUCTURE`; `SourceFactualClaim` with `sourceRole: TECHNICAL_TRUTH` → `AUTHORITATIVE_TECHNICAL_FACT`; with any other `sourceRole` → `SOURCE_FACTUAL_CLAIM`; `CandidateFactRequirement` → `FACT_REQUIREMENT_DERIVATION` **only** (§16.1) — never `AUTHORITATIVE_TECHNICAL_FACT`, since a technical source establishes the *answer* to a fact, never *whether the course requires it*. `ExemplarEvidence` carries mandatory provenance but no type-compatibility restriction beyond that.

## 15. Confidence model

Three independent dimensions on every candidate, each `HIGH / MEDIUM / LOW / NONE`: `scopeConfidence`, `depthConfidence` (basis tracked separately by `depthBasis`, §23), `technicalTruthConfidence` (governed now by claim-key coverage, §16, not subject matching). Two richer status fields make what the bare confidence level cannot express explicit: `technicalCoverageStatus` (`NOT_APPLICABLE / COMPLETE / PARTIAL / UNRESOLVED_REQUIREMENTS / CONFLICTED`, corrected by CC-20 — §22.2) and `knowledgeBoundaryStatus` (`STRUCTURALLY_DECOMPOSED / GOVERNED / PARTIAL / ADJUDICATION_REQUIRED / UNRESOLVED`, new in CC-20 — §22.1).

## 16. Independent factual claims, claim-key-exact coverage, and real conflict detection

CC-18A already made curriculum/provider and technical-truth claims independent `SourceFactualClaim` records correlated by `claimKey`, never one record naming the other's content as a pre-labelled conflict field. CC-18B tightens attachment and comparison further.

### 16.1 Candidate fact requirements (CC-18C: locked derivation model)

`CandidateFactRequirement { qualificationId, targetCandidateKey, claimKey, derivationStatus, sourceEvidenceRefs, ...provenance }` declares that a specific candidate structurally requires coverage for a specific `claimKey`. A candidate's `requiredFactKeys` come exclusively from these declarations — **zero** declared requirements means the candidate never claims `technicalTruthConfidence: HIGH` merely because some `TECHNICAL_TRUTH` source happens to discuss the same subject.

CC-18B left this record dangerously under-governed: `qualificationId` was optional, there was no citation requirement, and nothing stopped a normalization adapter hand-authoring the entire expected factual syllabus — making technical coverage *look* complete while never actually deriving from a real curriculum or assessment source. CC-18C closes this: `qualificationId` is now **mandatory** and validated exactly like `CandidateCapabilityRequirement` (§3, §11) — a foreign-qualification requirement never contributes a `requiredFactKey`. A locked `derivationStatus` (`factRequirementDerivationStatusSchema`) additionally gates every requirement:

- **`EXPLICIT_CURRICULUM_FACT`** — counts only when at least one `sourceEvidenceRefs` entry has `role: OFFICIAL_CURRICULUM` **and** its `evidenceId` resolves into the validated curriculum stream (§5).
- **`EXPLICIT_ASSESSMENT_FACT`** — counts only when at least one `sourceEvidenceRefs` entry has `role: PUBLIC_ASSESSMENT` **and** its `evidenceId` resolves into the validated assessment stream (§8).
- **`REVIEW_PROPOSED`** — exported for Project-Architect review via `EVIDENCE_NORMALIZATION_REVIEW`, but **never** contributes to `requiredFactKeys` or technical coverage automatically, unconditionally.

`validateCandidateFactRequirements` performs all of this — qualification match, real-target resolution, and citation eligibility — before a requirement is allowed to add a `requiredFactKey`; an ineligible requirement (wrong qualification, unmatched target, uncited `EXPLICIT_*_FACT`, or any `REVIEW_PROPOSED`) is excluded from the validated stream and reported, never silently promoted. `CandidateFactRequirement`'s own `normalizationBasis` is locked to `FACT_REQUIREMENT_DERIVATION` (§14) — `AUTHORITATIVE_TECHNICAL_FACT` is never valid here, because a technical source establishes the *answer* to a fact, never *whether the course requires it*.

### 16.2 Attachment is claim-key exact, multi-source resolution is deterministic, and multi-fact coverage is tracked explicitly

`attachFactualClaims` attaches `TECHNICAL_TRUTH` claims to a candidate only for `claimKey`s that are one of that candidate's `requiredFactKeys` (and whose `subject` matches). A technical claim sharing the candidate's *subject* but declaring an *unrelated* `claimKey` is never treated as satisfying a different required key. Results are collected per claim key in `factualStatementsByClaimKey` — the CC-18A/CC-18 singular `factualStatement = matches[0]` model, which silently discarded every fact beyond the first and was order-dependent, is removed entirely.

**CC-18C — multiple `TECHNICAL_TRUTH` claims for the same `(subject, claimKey)`.** CC-18B already deduplicated multiple *sources* onto one required key via the `requiredFactKeys` set, but its attachment logic still picked the technical claim via `.find(...)` — the *first* matching claim, silently ignoring any other `TECHNICAL_TRUTH` record for that exact `(subject, claimKey)`, which is source-order-dependent the moment two technical sources disagree. `attachFactualClaims` now collects **every** matching claim first, then resolves deterministically, never by array/source order:

- **zero** matching claims → the fact stays genuinely unresolved (no attachment, not counted covered);
- **one** matching claim → attaches normally;
- **more than one**, all sharing the same `comparisonKind` and the same `normalizedClaimValue` → attaches that shared value, and preserves **every** supporting claim's `EvidenceRef` (not just one) on the candidate;
- **more than one**, with **incompatible** `comparisonKind`s → emits `FACTUAL_COMPARISON_REVIEW` (§16.3); no value is attached, the fact is not counted as covered;
- **more than one**, with a **compatible** `comparisonKind` but **different** canonical values → emits `TECHNICAL_TRUTH_CONFLICT_REVIEW` (a new gap type, distinct from `FACTUAL_COMPARISON_REVIEW`'s incompatible-*kind* case — this is a disagreement *within* the same kind); no value is attached, the fact is not counted as covered, and no source order changes this outcome.

Coverage is computed deterministically from the *set* of required vs. attached keys, so source ordering never changes the result. **CC-20 correction:** a candidate with zero required keys no longer receives its coverage status here at all — `attachFactualClaims` leaves `technicalCoverageStatus` `undefined` in that case, deferring to `finalizeKnowledgeBoundary` (§22), which alone has the structural/adjudication context to tell a genuine structural node (`NOT_APPLICABLE`) apart from a mastery-bearing leaf that was simply never examined (`UNRESOLVED_REQUIREMENTS`) — collapsing both into one `NOT_REQUIRED` value was the exact false-green problem the blind back-test exposed. For a candidate with one or more required keys: `COMPLETE` (`technicalTruthConfidence: HIGH`, every required key attached, no disputed key among them), `CONFLICTED` (at least one required key hit an unresolved comparison-kind or value dispute — never silently folded into `PARTIAL`), `UNRESOLVED_REQUIREMENTS` (zero of the required keys attached and none disputed), or `PARTIAL` (`technicalTruthConfidence: MEDIUM`, some but not all attached, none disputed) otherwise. Because a disputed fact is never attached, a candidate with one undisputed and one disputed required fact reports `CONFLICTED`, distinctly from an ordinary partial-coverage case — a genuine technical dispute can never produce `COMPLETE`, and is never indistinguishable from simple incompleteness.

### 16.3 Comparison kinds gate conflict detection

`SourceFactualClaim.comparisonKind` (`BOOLEAN / ENUM / NUMBER_WITH_UNIT / CANONICAL_TEXT`) declares how `normalizedClaimValue` — a canonical comparison value, never arbitrary prose — may be compared. `detectFactualConflicts` groups claims by `claimKey` and, for each `TECHNICAL_TRUTH`/comparison-role pair sharing a key: if their `comparisonKind`s differ, it emits `FACTUAL_COMPARISON_REVIEW` (neither an automatic conflict nor a false agreement — incompatible kinds are never semantically reconciled by this package); only when the kinds match does it compare `normalizedClaimValue` for equality and emit `CURRICULUM_TECHNICAL_CONFLICT` on disagreement. Two claims that agree never produce a conflict record at all. This package performs no semantic/LLM comparison — canonicalisation is entirely the evidence author's responsibility, declared via `comparisonKind`.

The pipeline still, on a real conflict: retains curriculum's own authority over whether the topic is in scope (untouched); retains technical truth's own authority over what is taught (`factualStatementsByClaimKey` always comes from the `TECHNICAL_TRUTH` claim); preserves both source records; never teaches the incorrect source claim.

### 16.4 Diagnostic-only calibration comparison

`compareCalibrationFactualClaims(calibrationClaims, technicalClaims)` reuses the same claim-key/comparison-kind machinery to diagnostically compare `OPTIONAL_CALIBRATION` factual claims against approved `TECHNICAL_TRUTH` — supporting the real-world case where a provider handout contains an erroneous technical statement — without ever letting that comparison feed back into required-candidate generation (§13).

## 17. Exemplar provenance and the coverage boundary

`ExemplarEvidence` now carries mandatory `sourceRef`/`sourceLocator`/`normalizationBasis`, like every other scope-adjacent evidence type. A `TECHNICAL_TRUTH`-role exemplar does **not** itself set `technicalTruthConfidence: HIGH` merely because its role label says `TECHNICAL_TRUTH` — technical-truth coverage for *any* candidate, exemplar or otherwise, comes only from exact claim-key coverage under §16. Role and factual-truth confidence are kept structurally separate.

**CC-23A §9 note:** knowledge-boundary completeness (whether the approved learner-knowledge SET is sufficient, §22.4) and technical-evidence completeness (whether that knowledge's underlying facts are actually sourced/verified, the `COVERAGE GATE` above) remain two separate, independently-tracked axes -- exactly as already locked by §19/§22.4 for this package's own `knowledgeBoundaryStatus`/`technicalCoverageStatus` distinction. Nothing in CC-23A changes that lock; it only makes the diagram's stage NAMES and ORDER unambiguous end-to-end.

**Three distinct questions, three distinct governed stages (CC-21A).** It is deliberate that this sequence never collapses "is this true", "does this belong", and "is the resulting set enough" into one check: **technical truth** (§16) establishes only whether a proposition is factually/authoritatively correct — it has no opinion on inclusion or sufficiency; **fact-level semantic adjudication** (§21) decides only whether one already-proposed proposition belongs in required mastery — it has no opinion on whether the resulting *set*, once assembled, is complete; **knowledge-boundary certification** (§22.4) decides only whether the resulting set is sufficient — it can never re-litigate whether an individual fact is true or whether it belongs, and it can never manufacture a fact, adjudication, or candidate of its own. Conflating any two of these was the mechanism behind both CC-20's finding F (fact-level) and CC-21A's own false-green (candidate-level, §22.1/§22.4) — keeping them as three independently-validated stages, each with its own gap types, is what prevents a third recurrence.

This package produces `StandardPipelineResult` (`candidates`, `gaps`, `unmatchedTechnicalTruth`, `unmatchedQualificationLevel`, `semanticAdjudicationOutcomes`, `representativeExemplars`, and — CC-21A — `knowledgeBoundaryCertificationOutcomes`) and stops. Downstream course construction can distinguish, without inferring anything from prose: explicit required curriculum scope (`candidates` filtered by `disposition`); governing vs. unresolved learner knowledge (`requiredFactKeys` + `knowledgeBoundaryStatus`); accepted representative exemplars (`representativeExemplars`, never present in any candidate's `requiredFactKeys`); contextual/rejected knowledge (`semanticAdjudicationOutcomes` filtered by `decision`); the active certification (if any) behind a `GOVERNED`/`PARTIAL`/`UNRESOLVED` candidate (`knowledgeBoundaryCertificationOutcomes` filtered by `targetCandidateKey`); qualification-level-bounded vs. assessment-calibrated depth (`depthBasis`); technical coverage (`technicalCoverageStatus`, independently of `knowledgeBoundaryStatus` — §22.4); and unresolved semantic/certification decisions (`gaps` filtered by `SEMANTIC_ADJUDICATION_GAP`/`SEMANTIC_ADJUDICATION_CONFLICT`/`KNOWLEDGE_BOUNDARY_CERTIFICATION_GAP`/`KNOWLEDGE_BOUNDARY_CERTIFICATION_CONFLICT`).

### 19.1 Three-layer anti-cheating contract for the future blind back-test

The future Unit 202 normalization adapter is itself an audited product, not a trusted black box. It must preserve three layers **separately** and export all three:

- **A. Raw source locator** — the exact specification/assessment/technical-source locator a normalized item was derived from (`sourceRef`/`sourceLocator` on every evidence record already carries this).
- **B. Normalization proposal** — the adapter's own typed claim about what the source says: subject, performance, curriculum normalization kind, parent/family relationship, capability relationship, fact requirement, factual claim (the evidence record types in this package ARE this layer).
- **C. Pipeline acceptance** — accepted / rejected / review-required, and why (the `KnowledgeCandidate`/`GapRecord` output of `buildStandardPipeline` IS this layer).

No direct hand-authored "expected candidate" may bypass layer B — every candidate this package ever produces is traceable back through a typed, provenance-bearing normalization proposal to a raw source locator, and every rejection is equally traceable to exactly which validation gate declined it and why. An adapter that uses an LLM to *propose* normalized evidence (layer B) must still: preserve a real source locator for every proposal (layer A); have its structural mappings (registry resolution, category/family governance, capability derivation) validated against the governed registries by this package's own deterministic rules, never trusted from the model's own claim; keep uncertainty explicit (never force a `HIGH` confidence the evidence doesn't structurally support); and leave final curriculum authority with the Project Architect. "The model says this is the correct mapping" is never sufficient evidence on its own — only registry/relation resolution (this package's own deterministic logic) is.

## 21. Semantic adjudication (CC-20)

The blind back-test established that source normalization alone cannot safely decide whether a technically valid, non-literal knowledge proposal belongs in required mastery: automatically accepting every technically valid inferred fact overteaches some qualifications (finding C); automatically rejecting every non-literal fact is too conservative and leaves legitimate learner knowledge unresolved (finding D). Semantic judgement is therefore an explicit architectural **stage**, not something hidden inside source normalization or technical-source matching (finding G).

`SemanticAdjudication { qualificationId, targetCandidateKey, claimKey, decision, adjudicationBasis, adjudicatorKind, decisionRef, rationale, supportingEvidenceRefs, ...provenance }` is a governed **decision** over an **already-existing** `CandidateFactRequirement` proposal. It is explicitly **not** a new factual source (§2) — `validateSemanticAdjudications` rejects, as `EVIDENCE_NORMALIZATION_REVIEW`, any adjudication whose `(targetCandidateKey, claimKey)` does not resolve to a real, already-proposed `CandidateFactRequirement` for the active `qualificationId`, and any adjudication declaring a foreign `qualificationId`. It can never introduce a new curriculum candidate, `claimKey`, subject, or performance of its own — it can only resolve a question someone has already asked.

### 21.1 Decisions

Locked `semanticAdjudicationDecisionSchema`:

| Decision | Meaning | Governs a `REVIEW_PROPOSED` fact? |
|---|---|---|
| `REQUIRED_CORE` | Necessary learner knowledge to satisfy the qualification performance. | Yes |
| `REQUIRED_OPERATIONAL` | Operational/procedural knowledge inseparable from correctly performing the stated requirement. | Yes |
| `REPRESENTATIVE_EXEMPLAR` | A technically valid exemplar is needed to teach/instantiate a broad application, but this exact exemplar is not itself uniquely mandated mastery. | No — exposed via `representativeExemplars` instead (§21.2) |
| `CONTEXT_ONLY` | Pedagogically useful but not learner mastery. | No |
| `REJECT_OVERDEPTH` | Technically true but deeper/more formal than the qualification evidence justifies. | No |
| `REJECT_NOT_NECESSARY` | Technically true or related, but not necessary to satisfy the qualification performance. | No |
| `UNRESOLVED` | Available transferable evidence cannot safely determine the disposition. | No — emits `SEMANTIC_ADJUDICATION_GAP` (§21.4) |

Only `REQUIRED_CORE`/`REQUIRED_OPERATIONAL` (`GOVERNING_ADJUDICATION_DECISIONS`) may promote a `REVIEW_PROPOSED` `CandidateFactRequirement` into a governing `requiredFactKey`. `validateCandidateFactRequirements` (§16.1) checks, for a `REVIEW_PROPOSED` requirement, whether an **active** adjudication with a governing decision exists for the exact `(targetCandidateKey, claimKey)` — technical truth alone, qualification-level evidence alone, or a plausible rationale alone can never promote it (finding B, and CC-20 §7 of the task package). Promotion never widens curriculum scope: it can only add a `claimKey` to an **already-required** candidate's `requiredFactKeys`, never create the candidate itself. Whether the resulting `requiredFactKey` reaches `technicalCoverageStatus: COMPLETE` is governed entirely by §16.2's existing claim-key-exact attachment machinery, unaffected by adjudication — a `REQUIRED_CORE` decision with no matching `TECHNICAL_TRUTH` claim still governs, but still gaps via `TECHNICAL_TRUTH_GAP`.

`adjudicationBasis` (`semanticAdjudicationBasisSchema`: `SEMANTIC_NECESSITY / OPERATIONAL_NECESSITY / COMMAND_VERB_AND_LEVEL / PUBLIC_ASSESSMENT_CALIBRATION / MULTIPLE_VALID_IMPLEMENTATIONS / REPRESENTATIVE_EXEMPLAR_SELECTION / OVERDEPTH_FORMALISM / INSUFFICIENT_EVIDENCE`) records decision **reasons**, never evidence authorities in their own right — multiple bases may apply to one adjudication.

### 21.2 Non-governing decisions are preserved, never silently lost

`CONTEXT_ONLY`/`REJECT_OVERDEPTH`/`REJECT_NOT_NECESSARY` remain non-governing, but every ACTIVE (validated, non-conflicted) adjudication — governing or not — is preserved verbatim in `StandardPipelineResult.semanticAdjudicationOutcomes`, so a technically valid fact that was considered and deliberately excluded is auditable, never indistinguishable from one nobody ever looked at. `REPRESENTATIVE_EXEMPLAR` decisions are additionally surfaced in the dedicated `representativeExemplars: readonly RepresentativeExemplarRecord[]` collection — never present in any candidate's `requiredFactKeys`, never increasing scope or depth confidence, never masquerading as explicit curriculum or a required assessment proposition (finding C's overteaching risk, closed structurally rather than by convention).

### 21.3 Conflicting adjudications

Two or more validated adjudications giving incompatible `decision`s for the same `(qualificationId, targetCandidateKey, claimKey)` are never resolved by array order. `detectSemanticAdjudicationConflicts` excludes **every** adjudication sharing that identity from the active set and emits one `SEMANTIC_ADJUDICATION_CONFLICT` gap — no governing promotion occurs for that identity until the conflict is resolved, regardless of which adjudication happened to arrive first or last.

### 21.4 `UNRESOLVED`

An active adjudication resolving `UNRESOLVED` emits its own `SEMANTIC_ADJUDICATION_GAP` — the one decision that gets a dedicated gap type, because it is itself an admission that the available evidence was insufficient to decide (distinct from a deliberate `CONTEXT_ONLY`/`REJECT_*` closure, which needs no further resolution).

### 21.5 Adjudicator provenance — evidence-bound, never a trusted black box

`adjudicatorKind` (`HUMAN_PROJECT_ARCHITECT / LLM_EVIDENCE_BOUND / RULE_ENGINE`) records **who or what** performed the adjudication, but all three kinds pass through the exact same mechanical validation (§21) — an `LLM_EVIDENCE_BOUND` adjudication is never automatically trusted merely because of its label. `supportingEvidenceRefs` and `rationale` are mandatory precisely so the decision can be audited regardless of adjudicator: this is what allows a future qualification-specific adapter to use a frontier model for this semantic stage without making proprietary course-provider material a dependency of the stage itself — private course-provider material, where used at all, remains `OPTIONAL_CALIBRATION` (§2, §13) and is never required for semantic adjudication to operate.

### 21.6 `supportingEvidenceRefs` resolve mechanically against real accepted evidence (CC-20A; hardened CC-20B)

CC-20 introduced `supportingEvidenceRefs` but did not mechanically validate it — a fabricated `evidenceId`, a real `evidenceId` cited under the wrong role, or a real ref that simply doesn't pertain to the target candidate all validated merely because `sourceRef`/`sourceLocator` were non-empty and a matching `CandidateFactRequirement` proposal existed. CC-20A closed this: `validateSemanticAdjudications` resolves every `supportingEvidenceRefs` entry, by `(role, evidenceId)`, against the **same** validated evidence streams/registries the rest of `buildStandardPipeline` already produces — never a second, ungoverned evidence registry:

- `OFFICIAL_CURRICULUM` refs resolve against a map from validated `CurriculumEvidence` (excluding `DEPTH_QUALIFIER` records, which modify an existing candidate's depth rather than representing one themselves) to the exact `candidateKey` they create.
- `PUBLIC_ASSESSMENT` refs resolve against validated `AssessmentEvidence`'s own `candidateKey`.
- `QUALIFICATION_LEVEL` refs resolve against validated `QualificationLevelEvidence.appliesToCandidateKey`.
- `TECHNICAL_TRUTH` refs resolve against validated `TECHNICAL_TRUTH`-role `SourceFactualClaim` ids.

A ref only counts as a match when its role-appropriate registry resolves it to the **exact** `targetCandidateKey` the adjudication itself names — a real evidenceId belonging to a different candidate, or cited under the wrong role, resolves to nothing.

**Per-basis compatibility (`isBasisCompatibleWithSupport`).** Every basis in `adjudicationBasis` must itself be compatible with what actually resolved: `PUBLIC_ASSESSMENT_CALIBRATION` requires an `ASSESSMENT_MATCH` specifically; `COMMAND_VERB_AND_LEVEL` requires both a `CURRICULUM_MATCH` **and** a `QUALIFICATION_LEVEL_MATCH`; `SEMANTIC_NECESSITY`/`OPERATIONAL_NECESSITY` require a `CURRICULUM_MATCH` or `ASSESSMENT_MATCH` (a `TECHNICAL_TRUTH_REAL`-only ref may corroborate but never substitutes); `MULTIPLE_VALID_IMPLEMENTATIONS`/`REPRESENTATIVE_EXEMPLAR_SELECTION` require at least one genuinely resolved (non-fabricated) ref of any kind, since they are non-mastery bases by construction. **`OVERDEPTH_FORMALISM` (CC-20B correction)**: makes a qualification-**depth** judgement ("this technically valid knowledge is beyond the required learner depth") — a `TECHNICAL_TRUTH_REAL`-only match is **no longer sufficient** (CC-20A's original "any real match" rule was too weak: a factual authority can prove a proposition true without ever proving the qualification excludes it as over-depth). It now requires one of three routes: (A) `CURRICULUM_MATCH` **and** `QUALIFICATION_LEVEL_MATCH`; (B) `ASSESSMENT_MATCH` (assessment evidence is the pipeline's own depth-calibration mechanism); or (C) the target candidate's **own** already-resolved `depthBasis` is `EXPLICIT_CURRICULUM_DEPTH` (depth already governed by an explicit curriculum depth qualifier, without needing to re-cite it). `INSUFFICIENT_EVIDENCE` can never be compatible with a **governing** decision, but needs no evidence of its own for a non-governing one — it is the honest admission behind `UNRESOLVED`/`REJECT_*`.

**The gate applies to every adjudication, governing or not (CC-20B correction).** CC-20A applied the evidence-support/basis-compatibility check only to `REQUIRED_CORE`/`REQUIRED_OPERATIONAL`, silently exempting invalid `CONTEXT_ONLY`/`REJECT_*`/`REPRESENTATIVE_EXEMPLAR`/`UNRESOLVED` adjudications from any check at all — a malformed non-governing adjudication (e.g. a `REJECT_OVERDEPTH` citing a fabricated evidenceId) validated regardless, and could in principle be read as though it had legitimately vetoed something. CC-20B closes this: the basis-compatibility check now runs for **every** adjudication; only the additional "real curriculum/assessment authority for the exact candidate" requirement remains governing-decision-specific (a non-governing decision never needed that authority to begin with). Failing the gate rejects the whole adjudication — reported as `EVIDENCE_NORMALIZATION_REVIEW` (never silently dropped), for governing and non-governing decisions alike — regardless of `adjudicatorKind`: the label never bypasses the gate. A rejected adjudication, whatever its decision, is excluded from `active` entirely and so has **zero** semantic effect — it can never suppress an already-governing requirement, alter `knowledgeBoundaryStatus`, or influence any other adjudication's outcome.

## 22. Knowledge-boundary status and corrected technical coverage (CC-20)

The blind back-test's finding F: a leaf/mastery candidate with zero governing `requiredFactKeys` was reported identically to a candidate that structurally has no factual dimension at all (`technicalCoverageStatus: NOT_REQUIRED` either way) — reading as "technical knowledge is simply not required" even when the true state was "nobody has established what, if anything, is required yet." `finalizeKnowledgeBoundary` runs last in the pipeline, once `requiredFactKeys`/coverage and active adjudications are all known, and closes this.

### 22.1 `KnowledgeBoundaryStatus`

Computed for every `REQUIRED_EXPLICIT_CURRICULUM`/`REQUIRED_ASSESSMENT_EVIDENCED` candidate (undefined for prerequisite/exemplar/breadth-gap/review candidates, which this analysis never targets):

- **`STRUCTURALLY_DECOMPOSED`** — a genuine parent/category candidate whose required content is represented by governed child candidates. Detected from the **candidate-relationship graph** (a required child candidate's `parentSubject` naming this candidate's `subject`), never a topic string (finding requirement: "detect this from governed candidate relationships, not topic strings") — **and** (CC-20A correction) child existence is necessary but **not sufficient**: the parent must additionally be a demonstrably, explicitly structural curriculum node. Currently this means a validated `normalizationKind: RANGE_CATEGORY` record (`KnowledgeCandidate.isExplicitlyStructuralNode`, set only for `RANGE_CATEGORY`-kind candidates). A `PRIMARY_REQUIREMENT` is **never** `STRUCTURALLY_DECOMPOSED` merely because a `RANGE_REQUIRED_MEMBER` child's `refinesSubject` points at it, regardless of child count — it may itself carry an independent learner performance the children don't exhaust, so it falls through to the leaf analysis below (`UNRESOLVED`/`ADJUDICATION_REQUIRED`/`PARTIAL` as appropriate) like any other required candidate. This is deliberately conservative and extends only if real qualification evidence later justifies a governed exhaustive-decomposition relationship. No separate certification is required for a genuine structural node (§22.4).
- **`GOVERNED`** (**CC-21A correction — certification-gated; CC-21B narrows further**) — reachable **only** through a valid, non-stale, evidence-bound `KnowledgeBoundaryCertification` whose `decision` is `COMPLETE` (§22.4). Mechanically resolved fact coverage (`technicalCoverageStatus: COMPLETE`, no pending `REVIEW_PROPOSED` sibling) — or its deliberate absence, auditably closed at zero requirements by a resolved `SemanticAdjudication` — is **necessary** but is now **never sufficient** on its own: it is exactly the false-green CC-21A closes (revision history above). Without a valid `COMPLETE` certification at the current boundary fingerprint, the same mechanically-settled state instead reports `ADJUDICATION_REQUIRED` (see below) plus `KNOWLEDGE_BOUNDARY_CERTIFICATION_GAP`. **CC-21B:** a certification alone is also never sufficient — a boundary certification certifies an already **adequate** semantic boundary; it cannot certify the absence of decomposition for a non-structural, mastery-bearing candidate as `COMPLETE`, even when its `decision`, fingerprint, and supporting evidence are all otherwise valid (§22.4).
- **`PARTIAL`** — either (a) some governing requirements exist, no `REVIEW_PROPOSED` fact remains pending, but technical-truth coverage is incomplete and no certification is present, or (b) an active certification's `decision` is `PARTIAL` (§22.4).
- **`ADJUDICATION_REQUIRED`** — either (a) at least one `REVIEW_PROPOSED` `CandidateFactRequirement` targeting this candidate has not (yet) been promoted by an active governing adjudication, or (b) (**CC-21A**) the candidate's fact-level state is otherwise settled but no valid `COMPLETE` `KnowledgeBoundaryCertification` exists for it at the current boundary fingerprint — the corrected `GOVERNED` gate above.
- **`UNRESOLVED`** — either (a) a mastery-bearing leaf candidate with zero governing `requiredFactKeys`, no governed child decomposition, and **no adjudication history at all** — the exact false-green case finding F names, emitting `KNOWLEDGE_DECOMPOSITION_GAP` (§22.3) — or (b) (**CC-21A**) an active certification's `decision` is `UNRESOLVED` (§22.4).

### 22.2 Corrected `TechnicalCoverageStatus`

`NOT_REQUIRED` is retired. The replacement enum (`NOT_APPLICABLE / COMPLETE / PARTIAL / UNRESOLVED_REQUIREMENTS / CONFLICTED`) is detailed in §16.2 — in short, `NOT_APPLICABLE` is now reserved for genuinely structural/non-mastery-bearing cases (§22.1's `STRUCTURALLY_DECOMPOSED`, and non-`REQUIRED_*` dispositions), while a mastery-bearing leaf with zero established requirements reports `UNRESOLVED_REQUIREMENTS` — never rendered as though nothing is required.

### 22.3 `KNOWLEDGE_DECOMPOSITION_GAP`

Fires exactly when a required candidate has no governed child decomposition, no governing `requiredFactKeys`, and was never examined by any adjudication — never detected from a topic name, only from the structural/adjudication facts above. A genuine structural parent (§22.1's `STRUCTURALLY_DECOMPOSED`) never receives this gap merely because it has no facts of its own.

### 22.4 `KnowledgeBoundaryCertification` (CC-21A; CC-21B empty-boundary guard)

CC-21's rerun of the frozen Unit 202 back-test, reviewed semantically rather than merely mechanically, exposed a false-green CC-20/CC-20A/CC-20B never closed: `knowledgeBoundaryStatus: GOVERNED` was reachable purely because every currently-known `requiredFactKey` happened to be mechanically resolved (traced to a real proposal and, where needed, a real adjudication) with `technicalCoverageStatus: COMPLETE`. That proves the *known* requirements are individually satisfied — it never proves the *resulting set* is the right set. "Every governing fact currently on record checks out" and "this candidate's knowledge boundary is semantically complete" are different claims, and the pipeline was treating them as one.

`KnowledgeBoundaryCertification { qualificationId, targetCandidateKey, decision, adjudicatorKind, certificationRef, boundaryFingerprint, rationale, supportingEvidenceRefs, ...provenance }` is a governed **semantic certification** over an **existing** candidate's already-constructed knowledge state. Like `SemanticAdjudication` (§21), it is explicitly **not** a new evidence source (§2): it can never create a candidate, fact, `claimKey`, or requirement of its own, and it never widens scope. Where `SemanticAdjudication` answers "does this one proposition belong", `KnowledgeBoundaryCertification` answers a strictly later, independent question: "is the resulting set of governing facts (and/or governed child decomposition) sufficient for this candidate" (§19's three-distinct-questions framing).

**Decisions** (`knowledgeBoundaryCertificationDecisionSchema`): `COMPLETE` (the boundary is sufficient — the only decision that can produce `GOVERNED`), `PARTIAL` (some governing content exists but the boundary is knowingly incomplete — produces `PARTIAL`), `UNRESOLVED` (the reviewer cannot yet certify either way — produces `UNRESOLVED`, distinct from a candidate no certification has ever addressed, which remains `ADJUDICATION_REQUIRED`).

**`boundaryFingerprint` — the exact state a certification reviews.** `computeKnowledgeBoundaryFingerprint` hashes a canonical, key-sorted structure of: `qualificationId`, `targetCandidateKey`, `performanceType`, `performanceProvenance`, the candidate's current `requiredFactKeys`, every still-pending `REVIEW_PROPOSED` `claimKey` targeting the candidate, every active adjudication's `(claimKey, decision)` pair for the candidate, and the `candidateKey`s of its governed required children (§22.1's relationship graph) — every array sorted before hashing, so incidental insertion order never changes the result. `computeCandidateBoundaryFingerprints` computes this for every candidate from the same pending-fact/adjudication/child-decomposition state `finalizeKnowledgeBoundary` itself uses, so the two can never drift apart. A certification is **stale** — and never survives automatically — the moment its stored `boundaryFingerprint` stops matching the pipeline's current calculation: a fact proposal added or promoted, an adjudication decision changed, a performance-provenance change, or a governed child added/removed all change the fingerprint. A stale certification is rejected exactly like an absent one (`KNOWLEDGE_BOUNDARY_CERTIFICATION_GAP`, naming both fingerprints for audit).

**Validation gate (`validateKnowledgeBoundaryCertifications`), applied identically regardless of `adjudicatorKind`:** (a) provenance (§14); (b) `qualificationId` matches the active run; (c) `targetCandidateKey` resolves to a real, currently required candidate — never a fabricated key; (d) `boundaryFingerprint` exactly matches the current calculation (above); (e) at least one `supportingEvidenceRefs` entry mechanically resolves, by `(role, evidenceId)` against the same validated streams §21.6 already uses, to real `OFFICIAL_CURRICULUM` or `PUBLIC_ASSESSMENT` authority for the exact candidate — `TECHNICAL_TRUTH` may support factual correctness but can never, on its own, establish that a boundary is *complete* (the same asymmetry as §21.6's `OVERDEPTH_FORMALISM` correction: proving a fact true never proves a set sufficient); (f) a `COMPLETE` decision specifically is additionally invalid while any `REVIEW_PROPOSED` `CandidateFactRequirement` remains pending for the candidate — certification can never shortcut fact-level adjudication (§21). Every rejection at any gate is reported via `KNOWLEDGE_BOUNDARY_CERTIFICATION_GAP`, naming the exact failure, never silently dropped.

**Empty-boundary guard (CC-21B).** The validation gate above establishes that a certification is genuine, current, and well-evidenced — it says nothing about whether the candidate it targets has anything constructed to certify. `finalizeKnowledgeBoundary` closes that gap: a boundary certification certifies an already **adequate** semantic boundary; it cannot certify the absence of decomposition for a non-structural, mastery-bearing candidate as `COMPLETE`. For a candidate that is not itself an explicitly structural node (§22.1 — genuine structural exhaustion by governed children is detected and returned entirely by the earlier `STRUCTURALLY_DECOMPOSED` branch and never reaches this check), a `COMPLETE` certification is honoured only when the candidate has at least one governing `requiredFactKey`. A `COMPLETE` certification for a candidate with zero `requiredFactKeys` — whether that candidate was never examined by any adjudication (CC-20 finding F) or was examined and every proposal resolved non-governing (e.g. `CONTEXT_ONLY`/`REJECT_*`) — is rejected: it never suppresses the candidate's otherwise-correct, conservative status, and the rejection is itself reported via its own `KNOWLEDGE_BOUNDARY_CERTIFICATION_GAP`, never silently discarded. This guard is independent of `adjudicatorKind` — neither `HUMAN_PROJECT_ARCHITECT` nor `LLM_EVIDENCE_BOUND` bypasses it. A rejected certification still appears in `knowledgeBoundaryCertificationOutcomes` (it passed mechanical/evidence validation) — presence there is never itself evidence of `GOVERNED`; only `knowledgeBoundaryStatus` is.

**Conflicts.** Two or more validated certifications disagreeing on `decision` for the same `(qualificationId, targetCandidateKey, boundaryFingerprint)` are never resolved by array order — `detectKnowledgeBoundaryCertificationConflicts` excludes **all** of them from the active set (no `GOVERNED` for that candidate while conflicted) and emits one `KNOWLEDGE_BOUNDARY_CERTIFICATION_CONFLICT` gap.

**Technical coverage remains an independent axis.** A `COMPLETE` certification may legitimately coexist with `technicalCoverageStatus` short of `COMPLETE` and a visible `TECHNICAL_TRUTH_GAP` — certifying that the *set* of governing facts is the right set is a different judgement from whether every one of them already has attached technical-truth sourcing (§19's three-distinct-questions framing; the practical case is a Project-Architect certifying a boundary while flagging specific facts still needing technical sourcing). `finalizeKnowledgeBoundary` never uses `technicalCoverageStatus` to gate `knowledgeBoundaryStatus`; it reports the two independently.

**Structural nodes are unaffected.** A genuine `STRUCTURALLY_DECOMPOSED` parent (§22.1) needs no certification of its own — decomposition into governed children is itself the completeness argument for that node.

## 23. Depth basis and the corrected `PERFORMANCE_DEPTH_GAP` rule (CC-20)

The blind back-test attached valid Level-2 `QualificationLevelEvidence` to every candidate but still reported `depthConfidence: NONE` and `PERFORMANCE_DEPTH_GAP` for every one of them, purely because no `PUBLIC_ASSESSMENT` evidence existed (finding E) — too conservative: qualification-level evidence is real, governed depth information, even though it is weaker than an exact assessment-evidenced calibration.

### 23.1 `DepthBasis`

`EXPLICIT_CURRICULUM_DEPTH / ASSESSMENT_CALIBRATED / QUALIFICATION_LEVEL_BOUNDED / UNRESOLVED`, tracked alongside `depthConfidence` on every candidate:

- **`ASSESSMENT_CALIBRATED`** (`HIGH`) — `PUBLIC_ASSESSMENT` evidence resolved to this exact candidate (`generateAssessmentCandidates`).
- **`EXPLICIT_CURRICULUM_DEPTH`** (`HIGH`) — an explicit curriculum `DEPTH_QUALIFIER` resolved to this exact `(subject, performanceType)` candidate (§6.2). Raised from CC-18B's `MEDIUM` to `HIGH`: an explicit depth qualifier directly constrains depth and is no weaker a basis than assessment calibration.
- **`QUALIFICATION_LEVEL_BOUNDED`** (`MEDIUM`) — valid `QualificationLevelEvidence` attached to a required candidate that has **no stronger basis already resolved**. A defensible conservative **ceiling**, applied only in `attachQualificationLevelConstraints` when nothing stronger already won. Deliberately weaker and structurally distinguishable from `ASSESSMENT_CALIBRATED`/`EXPLICIT_CURRICULUM_DEPTH` — it never claims to know the exact content, formula, topology, or exemplar required (task rule: "qualification-level evidence...supplies a ceiling/bound, not hidden content"), and it never expands scope (unchanged: §2, `QUALIFICATION_LEVEL` is depth-only). **CC-20A correction:** level evidence bounds an **established** performance; it does not itself establish an uncertain one. The ceiling is gated on `KnowledgeCandidate.performanceProvenance` being `EXPLICIT` or `GOVERNED_INHERITED` — see the CC-20B correction immediately below for what actually qualifies as `EXPLICIT`. A candidate whose performance mapping is `UNRESOLVED` is left at whatever depth basis it already had; attaching a level descriptor to it never manufactures `MEDIUM` confidence out of an uncertain performance claim, and it remains eligible for `PERFORMANCE_DEPTH_GAP` (§23.3) where materially unresolved. Where frozen/historical evidence cannot mechanically prove `EXPLICIT`/`GOVERNED_INHERITED`, the pipeline conservatively reports depth as unresolved rather than the evidence being mutated to force a pass — an acceptable back-test outcome, never "fixed" by editing frozen input.

  **CC-20B correction — a populated performance enum is not itself `EXPLICIT` provenance.** CC-20A's original criterion for `EXPLICIT` was simply "`commandVerbPerformanceType`/`performanceType` is populated" — insufficient, because a populated enum is normalization **output**, not itself source evidence; a normalizer's own confident-but-inferred reading could reach `EXPLICIT` merely by filling the field in. A new field, `PerformanceEvidenceBasis` (`SOURCE_EXPLICIT` / `STRONG_INFERENCE`) — `CurriculumEvidence.commandVerbPerformanceBasis`, `AssessmentEvidence.performanceBasis` — now gates it: a populated performance enum counts toward `PerformanceProvenance.EXPLICIT` **only** when its accompanying basis is declared `SOURCE_EXPLICIT` (the performance/command is directly supported by source wording, or a mechanically governed explicit mapping — never a semantic guess). `STRONG_INFERENCE`, or the field left undeclared entirely, is treated identically — conservative by default, never assumed explicit. `GOVERNED_INHERITED` inherits this same requirement one level up: a `RANGE_REQUIRED_MEMBER` child may inherit `EXPLICIT`-equivalent standing only from a governed parent that is **itself** `SOURCE_EXPLICIT` — inheriting from a `STRONG_INFERENCE` parent can never upgrade the child into `GOVERNED_INHERITED`; it stays `UNRESOLVED`. Because CC-20A's frozen-evidence conservatism already applies (previous paragraph), this correction requires no change to any already-frozen evidence — an existing record with a populated verb but no declared basis simply continues to read as `UNRESOLVED`, which is the intended, conservative back-test behaviour.
- **`UNRESOLVED`** (`NONE`/`LOW`) — none of the above resolved. Merging two candidates (e.g. a curriculum-derived and an assessment-derived candidate for the same key) picks the higher-priority basis, mirroring the same ranking as `depthConfidence` so the two fields never disagree about which basis won.

### 23.2 `assessmentCalibrationAvailable`

Recorded independently of which basis ultimately won, so "no assessment evidence for this candidate" stays visible without collapsing into "total depth ignorance" — a `QUALIFICATION_LEVEL_BOUNDED` candidate still correctly reports `assessmentCalibrationAvailable: false`.

### 23.3 `PERFORMANCE_DEPTH_GAP`

The prior unconditional rule ("no assessment → gap, for every candidate") is removed. `computePerformanceDepthGaps` now fires only when `depthConfidence` is genuinely `NONE`/`LOW` after considering official curriculum, explicit performance, explicit depth qualifiers, qualification-level evidence, and available assessment evidence together — i.e., only when `depthBasis` never resolved past `UNRESOLVED`. `depthBasis` and `assessmentCalibrationAvailable` are both recorded on the gap itself for full traceability.

## 24. Testing this architecture

`packages/qualification-pipeline/src/rules.test.ts` proves synthetic regression cases A–O (CC-18), P–AC (CC-18A), AD–AZ (CC-18B), BA–BS (CC-18C), A–T (CC-20), BA2–BC2 (CC-20B), BD2–BS2 (CC-21A), and BT2–BY2 (CC-21B) — composite registry resolution and conflict detection, curriculum-evidence registry validation, the locked normalization-kind semantics (including Range members surviving as their own candidates and depth qualifiers not), multi-performance-type preservation, the validated-assessment-stream boundary (including rejection propagation into pattern/breadth computations), type-compatible provenance per evidence type, independent capability-dependency derivation kinds, claim-key-exact multi-fact technical coverage, comparison-kind-gated conflict detection, exemplar provenance, category/family governance against the known-subject set, semantic adjudication gating and conflict detection, knowledge-boundary status, knowledge-boundary certification, and the corrected depth-basis/`PERFORMANCE_DEPTH_GAP` model — using topic names chosen for readability only, never any real qualification's governed content. It also mechanically proves the package's own architectural boundaries: production source contains no qualification/topic-specific literal, and the package declares zero dependency on any other workspace package.

**CC-21A cases BD2–BS2** mechanically prove the knowledge-boundary-certification hardening (§22.4): BD2 — a governing fact with complete technical truth and no certification is `ADJUDICATION_REQUIRED`, never `GOVERNED` (the exact false-green closed); BE2 — the identical state plus a valid `COMPLETE` certification bound to the exact current fingerprint reaches `GOVERNED`; BF2/BG2 — a certification goes stale, and stops validating, when a new fact proposal is added or an adjudication decision changes after it was minted; BH2/BI2 — a certification citing fabricated curriculum evidence, or citing `TECHNICAL_TRUTH` alone, is invalid; BJ2/BK2 — `PARTIAL`/`UNRESOLVED` certifications produce the matching `knowledgeBoundaryStatus`; BL2 — a `COMPLETE` certification is invalid while an unresolved `REVIEW_PROPOSED` fact remains, even at an honestly-current fingerprint; BM2 — a `COMPLETE` certification may coexist with incomplete `technicalCoverageStatus` and a visible `TECHNICAL_TRUTH_GAP`, proving the two axes are independent; BN2 — two conflicting certifications at the same fingerprint never resolve by array order, in either direction; BO2/BP2 — a genuine structural `RANGE_CATEGORY` parent needs no certification of its own, while a `PRIMARY_REQUIREMENT` with children is never treated as structurally complete merely because children exist; BQ2 — a certification can never create a candidate, fact, `claimKey`, or scope of its own; BR2 — `HUMAN_PROJECT_ARCHITECT` and `LLM_EVIDENCE_BOUND` certifications pass through the identical mechanical gate; BS2 — the boundary fingerprint is deterministic and array-order-independent, and changes only when the underlying logical state genuinely changes.

**CC-21B cases BT2–BY2** mechanically prove the empty-boundary certification guard (§22.4): BT2 — a `COMPLETE` certification cannot certify an empty, unexamined knowledge boundary (never `GOVERNED`, `KNOWLEDGE_DECOMPOSITION_GAP` and its own `KNOWLEDGE_BOUNDARY_CERTIFICATION_GAP` both visible, the rejected certification still auditable in `knowledgeBoundaryCertificationOutcomes`), and the identical guard applies when the candidate WAS examined by an adjudication that resolved to nothing governing; BU2/BV2 — `HUMAN_PROJECT_ARCHITECT`/`LLM_EVIDENCE_BOUND` identity is never a bypass for this guard; BW2 — a candidate with a real governing fact/procedure boundary is unaffected and can still reach `GOVERNED`; BX2 — an explicit structural `RANGE_CATEGORY` with governed children and zero own facts remains `STRUCTURALLY_DECOMPOSED` with no false certification requirement; BY2 — a `PRIMARY_REQUIREMENT` with children but zero own governing knowledge cannot exploit child existence as automatic exhaustive decomposition, even with an otherwise-valid `COMPLETE` certification.

**CC-18C cases BA–BS** mechanically prove the five defect corrections: BA/BB/BC — a blank-provenance `CurriculumEvidence`, `AssessmentEvidence`, or `OfficialCurriculumUnit` is rejected and reported, never silently dropped; BD/BE/BF/BG/BH — a foreign-qualification, uncited, role-mismatched-citation, or `DETERMINISTIC_OPERATIONAL_DEPENDENCY` capability requirement cannot auto-promote a prerequisite, while a properly qualification-bound, role-and-id-cited `EXPLICIT_CURRICULUM_OPERATION` can; BI/BJ/BK/BL — a foreign-qualification, `REVIEW_PROPOSED`, or uncited `EXPLICIT_*_FACT` fact requirement never contributes a `requiredFactKey`; BM/BN/BO/BP/BQ — agreeing multi-source technical claims attach with every ref preserved, disagreeing claims (same or reversed order) produce `TECHNICAL_TRUTH_CONFLICT_REVIEW` with no arbitrary attachment, incompatible comparison kinds produce `FACTUAL_COMPARISON_REVIEW`, and one disputed required fact reports `CONFLICTED` (CC-20; previously capped at `PARTIAL`); BR/BS — an explicitly-targeted `DEPTH_QUALIFIER` affects only its exact `(subject, performanceType)` candidate, and an ambiguous one (no explicit target, more than one performance type) applies to neither and is reported for review.

## 25. Evidence-requirement planning and technical-evidence acquisition (CC-23)

**Package:** `@alp/technical-evidence-engine` (`packages/technical-evidence-engine/src/`). **Design authority for the package boundary decision:** `docs/architecture/adr/ADR-0007-technical-evidence-acquisition-planning.md`. This section documents the pipeline design; the ADR documents why the responsibility lives in a NEW package rather than being folded into this package or into the pre-existing, unrelated `@alp/evidence-engine` (learner mastery/attempt evidence — a different domain entirely, see ADR-0007 §Context).

### 25.1 Why this stage exists, and where this package's own responsibility ends

This package (`@alp/qualification-pipeline`) answers exactly one question: **what must the learner know/do?** Its `StandardPipelineResult` is the complete, final answer — candidates, gaps, semantic adjudications, knowledge-boundary certifications. It has never answered, and must never be extended to answer, a second question: **what factual/procedural/source evidence must exist to support that already-approved knowledge?** That second question is `@alp/technical-evidence-engine`'s entire scope, and it begins only AFTER a Project-Architect curriculum decision has selected the approved learner-knowledge boundary from this package's output — never before, and never in place of it.

### 25.2 Locked separation of authorities (task CC-23 §4)

| Question | Answered by |
|---|---|
| What must the learner know/do? | `@alp/qualification-pipeline` (this document, §1-§24) |
| What factual/procedural/source evidence must exist to support that already-approved knowledge? | `@alp/technical-evidence-engine`'s `EvidenceRequirementPlanner` (§25.3-§25.5 below) |
| Is the technical/factual content correct? | The future technical-evidence ACQUISITION engine (§25.6 — contract only, not implemented) |

Technical sources can never create qualification scope, broaden performance, increase curriculum depth, or turn contextual material into required mastery — the acquisition system searches only for evidence needed by an ALREADY-authorised knowledge boundary. Mechanically: every `EvidenceRequirement` the planner emits traces back to at least one `sourceKnowledgeTargetId` it was handed; the planner has no code path that invents a `KnowledgeTarget` of its own.

### 25.3 `KnowledgeTarget` ≠ `EvidenceRequirement`

`KnowledgeTarget` (learner-facing semantic knowledge/performance) → 0..N `EvidenceRequirement`s (sourceable evidential obligations). `EvidenceRequirement` → 1..N `KnowledgeTarget`s. Both directions are real production types (`packages/technical-evidence-engine/src/types.ts`), never a Unit-202-specific JSON report shape.

`KnowledgeTarget.kind` is one of eleven generic semantic classes (never a subject-specific branch): `CONCEPT_DEFINITION`, `FACTUAL_PROPOSITION`, `FORMULA_OR_RULE`, `RELATIONSHIP`, `PROCEDURE`, `SYMBOL_OR_CONVENTION`, `OPERATIONAL_USE_RULE`, `OPERATING_PRINCIPLE`, `RECOGNITION_REQUIREMENT`, `APPLICATION_FUNCTION`, `BREADTH_TOPIC_COVERAGE`. `KnowledgeTarget.classification` reuses the locked four-class model (`REQUIRED_QUALIFICATION_KNOWLEDGE` / `FOUNDATIONAL_PREREQUISITE` / `CONTEXTUAL_TEACHING_SUPPORT` / `OUT_OF_SCOPE`).

### 25.4 Decomposition behaviour (task §8) — driven entirely by structural fields, never by text content

`planEvidenceRequirements` (`planner.ts`) never inspects what a target's free-text description SAYS — only what its structural fields DECLARE:

- **A. Atomic fact** (`FACTUAL_PROPOSITION`/`FORMULA_OR_RULE`/`SYMBOL_OR_CONVENTION`/`OPERATIONAL_USE_RULE`/`OPERATING_PRINCIPLE`/`APPLICATION_FUNCTION`/`RECOGNITION_REQUIREMENT`, or a single-claim `RELATIONSHIP`) → one `EvidenceRequirement`, `decompositionStatus: READY`, `requirementMode` derived deterministically from `kind`.
- **B. Compound knowledge target** — a `CONCEPT_DEFINITION` target with `expectedCoverageDimensions.length > 1` → one `EvidenceRequirement` PER requested coverage dimension, each independently addressable (own `canonicalRequirementKey`), never bundled into one opaque requirement.
- **C. Procedural skill** — a `PROCEDURE` target → `requirementMode: PROCEDURE_COVERAGE`, requiring actual procedure coverage, never a sentence merely containing the topic name (enforced by the mode's acceptance criterion, §25.5).
- **D. Broad topic/breadth target** — a `BREADTH_TOPIC_COVERAGE` target → `requirementMode: TOPIC_BREADTH_COVERAGE`, requiring substantive authoritative topic/procedure coverage, never a fake single exact-fact sentence.
- **E. Integration target** — a `RELATIONSHIP` (or, CC-23A: `FORMULA_OR_RULE`) target with `requiresMultipleIndependentClaims: true` AND `constituentKnowledgeTargetIds` (≥2) declared → ZERO new evidence requirements; recorded instead as `StructuralSatisfactionRecord{ kind: "INTEGRATION_SATISFIED_BY_CONSTITUENTS" }`, satisfied by its constituents' own already-planned requirements rather than a manufactured redundant combined-relationship source.
- **E2. Formula/relationship + rearrangement (CC-23A §11-§15)** — a `RELATIONSHIP`/`FORMULA_OR_RULE` target with `requiresMultipleIndependentClaims: true` AND `reusesFoundationalProcedureIds` (≥1) declared → ONE `EvidenceRequirement` covering the formula/relationship itself (`decompositionStatus: READY`, dimensions `[FORMULA, FORMULA_INTERPRETATION]` — the authoritative formula AND the meaning of its variables), PLUS a `StructuralSatisfactionRecord{ kind: "REARRANGEMENT_SATISFIED_BY_FOUNDATIONAL_PROCEDURE" }` recording that the rearrangement/substitution/use dimension is satisfied by an already-approved foundational procedural capability — never a second technical-domain source proving ordinary algebraic manipulation. Generalizes the rule: TECHNICAL FORMULA/RELATIONSHIP → its own source; REARRANGEMENT/SUBSTITUTION/USE → the generic governed formula-transposition/calculation capability, UNLESS a domain imposes a special procedural constraint beyond ordinary algebra, which is then its own separate target with its own evidence requirement.
- **F. Structural/parent target** — a target with `childKnowledgeTargetIds` populated → ZERO new evidence requirements; `StructuralSatisfactionRecord{ kind: "STRUCTURAL_PARENT_DECOMPOSED" }`.
- **G. Under-specified target** — a `CONCEPT_DEFINITION` with no (or one) `expectedCoverageDimensions`, or a multi-claim `RELATIONSHIP`/`FORMULA_OR_RULE` with neither declared constituents NOR a foundational-procedure reuse → `decompositionStatus: SEMANTIC_DECOMPOSITION_REQUIRED`, a non-null `decompositionReason`, and an acceptance criterion of "not yet determinable" — the planner abstains rather than inventing a decomposition, and the gap is returned to the Project Architect (task §27, never "forced to zero gaps").

`OUT_OF_SCOPE` targets are never sourced at all (`StructuralSatisfactionRecord{ kind: "OUT_OF_SCOPE_EXCLUDED" }`) — §25.2's separation-of-authorities rule enforced mechanically.

**CC-23A §17-§19 — directional/operational rules.** A directional, spatial, or hand-rule-style operational rule (a right-hand grip rule, a generator rule, a compass back-bearing rule) is represented as an ordinary `OPERATIONAL_USE_RULE` target (class A, atomic, immediately `READY`) carrying an OPTIONAL `directionalMapping` array (`{ role, meaning }` pairs) as structured, generic audit/provenance metadata. The planner never interprets or branches on `directionalMapping` content — it exists purely so a domain can express directional knowledge without inventing a domain-specific production field (task §CH), proven with a non-electrical fixture (a compass bearing rule) in `planner.test.ts`.

### 25.5 Canonical reuse, coverage dimensions, source authority, and acceptance (task §9-§12; CC-23A §2-§7 hardening)

**CC-23A correction:** CC-23's original `canonicalRequirementKey` was normalized DISPLAY TEXT + `requirementMode` — insufficient, because identical human-readable wording does not guarantee identical technical meaning (homonyms: "range" in statistics vs. measurement; "power" in mechanics vs. as an electrical quantity), and Project-Architect review found this a genuine safety gap for cross-domain reuse. `canonicalRequirementKey` is now derived from `KnowledgeTarget.semanticIdentity` (`{ semanticNamespace, semanticKey }`, mandatory on every `KnowledgeTarget`) + `requirementMode` (+ coverage dimension, for compound sub-requirements) — qualification location, AC number, awarding organisation, course ID, and learner-target ID are never part of this identity, and neither, now, is display text. `requirementText` remains presentation/audit material only; it has no bearing on identity or reuse.

Two targets whose `semanticIdentity` is equal are the same reusable technical truth regardless of wording, qualification, or requirement mode differences that don't affect the key itself; two targets whose display text is equal but `semanticIdentity` differs are NEVER merged (a homonym is now structurally impossible to collapse by accident). Because `requirementMode` is part of the key, two targets sharing a semantic identity but needing incompatible requirement modes (e.g. a definition vs. a procedure for the same concept) never silently collapse into one evidence obligation either.

`planEvidenceRequirements` accepts an optional `existingRequirements` accumulator; calling it once per qualification and threading that accumulator through makes a shared canonical technical truth (e.g. a physical law required by two different qualifications) collapse into ONE `EvidenceRequirement` whose `sourceKnowledgeTargetIds` spans both — sourced and verified once, reused everywhere, never re-sourced per qualification, and never decided by text equality alone.

**CC-23A §6 — the permanent handoff requirement.** The generic planner does not, and will never, discover semantic identity from `targetText` via fuzzy NLP or word matching — `semanticIdentity` must be supplied as STRUCTURED metadata by whichever party approves the learner-knowledge boundary (the upstream semantic-construction step for a real future qualification; a qualification-specific adapter standing in for it during regression testing, as Unit 202's does). This is a **permanent architectural handoff requirement**: any future qualification ingestion pathway must hand technical-evidence planning genuine structured semantics, not merely free-text propositions, or safe canonical reuse cannot be established for it.

`requiredCoverageDimensions` draws from a reusable, extensible seventeen-value set (`DEFINITION`, `QUANTITY_SYMBOL`, `UNIT_NAME`, `UNIT_SYMBOL`, `DISTINCTION`, `FORMULA`, `FORMULA_INTERPRETATION`, `PROCEDURE`, `CONNECTION_TOPOLOGY`, `SAFE_USE`, `CAUSAL_MECHANISM`, `OPERATING_PRINCIPLE`, `SCHEMATIC_SYMBOL`, `APPLICATION_FUNCTION`, `CALCULATION_METHOD`, `RECOGNITION`, `CONCEPTUAL_RELATIONSHIP`) — illustrative of a technical-qualification domain, never electrical-only, and never treated as closed.

**CC-23A §7 correction — extensible authority taxonomy.** CC-23's `SourceAuthorityClass` was a closed zod enum of seven electrical/engineering-flavoured classes, which would have required a production-code change every time a new domain (construction, plumbing, automotive, healthcare, laboratory science, legal/regulatory training, computing, ...) needed a legitimate authority class this package's authors never anticipated. `SourceAuthorityClass` is now an OPEN string type: `STANDARD_AUTHORITY_CLASSES` (`PRIMARY_NORMATIVE_OR_STANDARDS_BODY`, `GOVERNMENT_OR_REGULATOR`, `ACADEMIC_OR_RESEARCH_INSTITUTION`, `PROFESSIONAL_BODY`, `ORIGINAL_MANUFACTURER_OR_VENDOR`, `AUTHORITATIVE_TECHNICAL_REFERENCE`, `AUTHORITATIVE_EDUCATIONAL_REFERENCE`) are useful, domain-neutral defaults `DEFAULT_SOURCE_AUTHORITY_POLICY` relies on, never an exhaustive closed set. A domain policy may introduce any additional class string of its own (e.g. a maritime classification society, a pharmacopoeia authority) purely through the `SourceAuthorityPolicy` it supplies — zero planner code change required. No real institution is ever named in this package; both the standard classes and any domain-added ones are later-discovered INSTANCES the acquisition engine supplies.

**CC-23A §8 — authority never creates scope (regression-protected).** `SourceAuthorityPolicy` selects acceptable evidence authority ONLY. It structurally cannot create learner knowledge, expand qualification scope, set curriculum depth, or promote contextual material — the type has no field capable of expressing any of those, and `planEvidenceRequirements` never reads `sourceAuthorityPolicy` when computing `classification`, `acquisitionPriority`, or `decompositionStatus`. Proven directly: two runs of the identical `KnowledgeTarget` under two different authority policies produce identical `acquisitionPriority`/`decompositionStatus`/`requirementMode`, differing only in `sourceAuthorityClasses` (planner.test.ts §CJ).

Acceptance criteria (`acceptanceCriteria`) are likewise keyed on `requirementMode`, never a universal "one source states it verbatim" rule — a `PROCEDURE_COVERAGE` requirement demands the source actually teach the procedure, a `TOPIC_BREADTH_COVERAGE` requirement demands substantive breadth coverage, and every mode's criterion explicitly states that a source title alone never satisfies it.

### 25.6 The future technical-evidence acquisition contract (task §14) — defined, not implemented

`TechnicalEvidenceAcquisitionRequest` (`evidenceRequirements[]`, `sourceAuthorityPolicy`, `acquisitionPolicy`) and `TechnicalEvidenceAcquisitionResult` (`candidateSources[]`, `normalizedClaims[]`, `verificationStatus`, `conflicts[]`, `gaps[]`) are declared in `types.ts` as the contract the NEXT package will implement and execute. `@alp/technical-evidence-engine` itself contains zero network, filesystem-read, or browsing code — mechanically proven by an architecture-integrity test that greps production source for I/O call signatures (`fetch(`, `readFileSync`, `http.request`, etc.). The planner and the (future) acquirer are permanently separate: planner takes approved knowledge to evidence requirements; acquirer takes evidence requirements to sources. This package may never do the acquirer's job, no matter how tempting a "just fetch it while we're here" shortcut looks.

### 25.7 Generic experiment isolation (task §15/§21)

`LocalAccessGuard` (`access-guard.ts`) is a generic, config-driven local-read guard: a `LocalAccessGuardConfig` (exact paths and/or globs, optional required content hashes) is the ONLY source of truth for what a blind-acquisition experiment may read from its own local repository. Every read must go through `checkRead`; a non-allowlisted path throws `UnauthorizedLocalReadError` immediately (default deny — absence from the allowlist, not presence on any denylist, is what denies), and a hash-pinned rule whose actual content hash disagrees throws `LocalInputIntegrityError` immediately — both unrecoverable, per task §13's access-audit contract (experiment invalid, no continuation). `getAuditLog()` returns the complete, ordered trail (`canonicalPath`, `contentHash`, `reason`, `matchedRule`, `outcome`, `recordedAt`) for every read attempted, allowed or denied. A qualification-specific denylist (if a qualification's own harness keeps one) is defence-in-depth documentation only — the guard itself never consults it.

### 25.8 Architecture governance rules (task §22) — permanent, recorded here

1. Learner knowledge (`KnowledgeTarget`/`KnowledgeCandidate`) and technical evidence requirements (`EvidenceRequirement`) are separate entities, never merged into one type.
2. Technical evidence can never author qualification scope (§25.2).
3. One learner target may require many evidence requirements (§25.3).
4. One technical evidence requirement may satisfy many learner targets and many qualifications (§25.5).
5. Technical truths are canonical domain assets, not qualification-local duplicates (§25.5).
6. Broad topics/procedures do not become fake factual sentences merely to fit source retrieval (§25.4.D).
7. Under-specified decomposition causes an explicit gap, never invention (§25.4.G).
8. Source authority is requirement-dependent (§25.5).
9. Exact locator verification is mandatory before factual coverage — carried into the future acquisition contract's `requireExactLocator`/`retrievedPassage` fields (§25.6); this package's own acceptance criteria universally reject a source-title-only match.
10. Historical/private/provider evidence is never required for generic operation — the planner's input contract (`KnowledgeEvidencePlanningInput`) contains no historical-dossier concept anywhere; a qualification with no historical dossier at all uses the identical planner.
11. Qualification-specific back-tests (e.g. the Unit-202 preflight harness) may validate this architecture but must never define its production semantics — enforced by the dependency-direction rule (§25.9).
12. The same pipeline must operate when there is no existing source dossier — nothing in `@alp/technical-evidence-engine` reads, or knows the shape of, any historical dossier.

### 25.9 Dependency direction (task §23) — mechanically enforced

`packages/technical-evidence-engine/**` must never import from `scripts/backtests/**`, `reports/**`, any qualification-specific data, legacy lessons/assertions, or private calibration material. A qualification-specific adapter (e.g. `scripts/backtests/unit202-evidence-acquisition-preflight/`) MAY import from `@alp/technical-evidence-engine` — never the reverse. Proven by: (a) the package's own architecture-integrity tests (`planner.test.ts`) asserting zero `@alp/*` dependency in `package.json` and zero `@alp/*` import in production source (mirroring `@alp/qualification-pipeline`'s identical pattern, §24); (b) a dedicated dependency-direction test in the Unit-202 preflight harness asserting the reverse import never occurs.

### 25.10 Testing this stage

`packages/technical-evidence-engine/src/planner.test.ts` proves synthetic, non-electrical regression cases §16.A-H (a mathematics procedure; a mechanical/scientific compound concept; a non-electrical operating principle; a broad topic target; an integration target; cross-qualification canonical reuse; a contextual target; an under-specified target), CC-23A cases §CA-§CJ (semantic-identity-driven cross-qualification reuse with differing wording; homonym non-collision across differing namespaces; incompatible-requirement-mode non-collision; qualification-ID-independent reuse; within-qualification reuse; the generic formula+rearrangement rule, including in a non-electrical fluid-dynamics fixture; domain-agnostic directional-mapping representation; a custom domain authority class supplied purely via policy; authority policy's inability to affect classification/priority/decomposition), plus additional structural/scope coverage (a structural/parent target; an `OUT_OF_SCOPE` target; deterministic array-order-independent output; caller-supplied authority-policy override), and mechanically proves this package's own architectural boundaries (zero qualification/electrical-specific literal in production source, zero `@alp/*` dependency, zero I/O in the planner, no qualification-name-branching conditional, no free-text semantic-identity discovery, `SourceAuthorityClass` never a closed zod enum). `packages/technical-evidence-engine/src/access-guard.test.ts` proves the generic local-input isolation utility: positive-allowlist matching (exact path and glob), default-deny on an unlisted path, hash-pinned integrity failure, and the full access-audit record shape. The Unit-202 preflight harness (`scripts/backtests/unit202-evidence-acquisition-preflight/`) is the qualification-specific regression fixture proving the SAME generic behaviour against real frozen Unit-202 data — never the source of the generic behaviour itself.

### 25.11 CC-23A Unit-202 gap resolution — proof the generic mechanisms suffice

All 8 of CC-23's own Unit-202 preflight `SEMANTIC_DECOMPOSITION_REQUIRED` gaps are resolved using ONLY the generic mechanisms above, entirely from the Unit-202 ADAPTER (never from new generic planner code): three formula targets (`R = ρL/A`, `V = IR`, `B = Φ/A`) and the frequency/pole-pairs relationship reclassified to `FORMULA_OR_RULE` with `reusesFoundationalProcedureIds` pointing at Unit 202's own existing "formula transposition" foundational-procedure target (class E2, §25.4); the duplicate frequency learner target (two differently-worded propositions for the identical calibrated relationship) given the SAME explicit `semanticIdentity` so they merge into one canonical requirement while both source mappings are preserved in `sourceKnowledgeTargetIds` (§25.5); and three directional rules (right-hand grip, Fleming's left-hand, Fleming's right-hand) reclassified to `OPERATIONAL_USE_RULE` (already class A, atomic) carrying structured `directionalMapping` metadata. No new gap was exposed by the corrected identity rules for this frozen target set.

**CC-20 cases A–T** mechanically prove the semantic-adjudication and knowledge-boundary hardening: A/B — a zero-fact required leaf is `UNRESOLVED`/`KNOWLEDGE_DECOMPOSITION_GAP`, never `NOT_APPLICABLE`, while a genuine structural parent with governed children is `STRUCTURALLY_DECOMPOSED` with no false gap; C/D/E/F — a `REVIEW_PROPOSED` fact stays non-governing (`ADJUDICATION_REQUIRED`) until an active `REQUIRED_CORE`/`REQUIRED_OPERATIONAL` adjudication promotes it, and promotion never bypasses the existing technical-truth-gap machinery when coverage is still missing; G — `REPRESENTATIVE_EXEMPLAR` is exposed via `representativeExemplars` and never enters `requiredFactKeys`; H/I/J/K — `CONTEXT_ONLY`/`REJECT_OVERDEPTH`/`REJECT_NOT_NECESSARY` remain non-governing but are preserved in `semanticAdjudicationOutcomes`, and `UNRESOLVED` emits `SEMANTIC_ADJUDICATION_GAP`; L/M — an adjudication referencing a nonexistent fact proposal, or belonging to a different qualification, is rejected and cannot influence the result; N — two conflicting adjudications for the same fact never resolve by array order, in either direction; O/P/Q/R — qualification-level evidence alone bounds depth to `MEDIUM` (`QUALIFICATION_LEVEL_BOUNDED`) rather than `NONE`, absence of assessment alone no longer causes `PERFORMANCE_DEPTH_GAP`, qualification-level evidence still creates zero scope/facts, and `ASSESSMENT_CALIBRATED` remains distinguishable from `QUALIFICATION_LEVEL_BOUNDED` when both are present; S/T — a governing fact alongside a still-pending review-proposed sibling is never falsely `COMPLETE`, and technical truth alone, with no adjudication at all, can never convert a `REVIEW_PROPOSED` fact into required mastery.
