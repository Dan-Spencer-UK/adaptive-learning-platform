# Premium Instructional Visual Production Pipeline

**Project:** Adaptive Learning Platform
**Status:** Approved durable design specification — production methodology and art-direction governance (Product Owner / Project Architect, 2026-08-23). **Not approved by this document**: any specific piece of artwork, any specific reference image's fitness for use, any specific vendor/tool selection for image generation. This document governs *how* premium instructional artwork is produced and *what technical authority it does and does not carry* — it does not itself approve, commission or generate anything.
**Applies to:** every instructional visual the platform ever produces, across every qualification, present and future — the same universal scope as [`CC-05D`](CC-05D-INSTRUCTIONAL-VISUAL-GOVERNANCE-AND-SEMANTIC-QA.md).
**Follows / extends:** [`CC-05D-INSTRUCTIONAL-VISUAL-GOVERNANCE-AND-SEMANTIC-QA.md`](CC-05D-INSTRUCTIONAL-VISUAL-GOVERNANCE-AND-SEMANTIC-QA.md) (the governed-contract/mechanical-QA/semantic-QA architecture for how a visual is *validated*) and [`ADR-0004`](adr/ADR-0004-deterministic-authority-over-generated-instructional-imagery.md) (the hard authority boundary between deterministic technical geometry and generated imagery). This document is the *production methodology* layer: how a visual is *made* before it ever reaches CC-05D's QA pipeline.
**Design intent:** instructional visuals for a paid, category-leading consumer learning product must be premium, technically correct and pedagogically clear at once — never trading one for another. This document records how those three requirements are reconciled without introducing an unverified AI-imagined-geometry dependency into anything a learner is assessed against.

---

## 1. Instructional visuals are governed content, not decoration

A visual can encode topology, geometry, direction, sequence, spatial relationships, component recognition, formula relationships, misconceptions and assessment evidence. Visual correctness and visual completeness are therefore part of learner-content quality, on the same footing as a governed assertion's factual correctness — not a cosmetic layer applied afterward. This is the founding premise CC-05D already established (its §2: "not acceptable merely because it type-checks, renders, and structurally snapshot-matches"); this document extends the same premise to *how the artwork itself is produced*, not only how it is checked once it exists.

## 2. Visual production classes

Every instructional visual should be classified as one of three production classes. The classification is a property of the visual family, decided once and recorded alongside its governed contract (§7):

- **A. DETERMINISTIC TECHNICAL** — for content where exact geometry is itself the taught or assessed fact: circuit diagrams, UK/IEC schematic symbols, waveforms/graphs, formula visuals, mathematical geometry, instrument connections, exact force/current/field/motion relationships, and any assessment answer geometry. Produced as deterministic vector renderers (the existing `apps/mobile/src/components/diagrams/*` pattern), never as generated raster imagery. Every visual currently governed under CC-05D (all 16 diagram blueprints as of CC-11.3) is class A.
- **B. PREMIUM CONCEPTUAL ILLUSTRATION** — for physical/intuitive concepts where exact technical geometry is not itself the assessed fact: e.g. a workshop context photo-realistic impression, a material-texture comparison, an "apprentice using a tool" scene. Exact pixel geometry is not load-bearing; finish, mood, and intuitive recognisability are.
- **C. HYBRID** — a premium illustrated physical/context layer (class B) with deterministic technical overlays (class A) composited on top — e.g. a premium-illustrated motor housing with a deterministic force-arrow/pole-label overlay. **Hybrid is preferred wherever premium presentation is valuable but technical truth must remain exact** — it is not a compromise class, it is the default target for any visual that has both a "look premium" need and a "must be exactly correct" need.

No visual currently in the corpus is produced as class B or C — every one built through CC-05C/CC-05D/CC-11.x is class A, functional but not yet premium artwork (see §11's honest status record). Classes B and C describe the target state this pipeline exists to reach, not work already done.

## 3. Human-readable reference-first workflow

Do not default to an LLM or image generator inventing instructional visuals from first principles. The required production sequence for any new or replaced visual family:

```text
GOVERNED CONCEPT
  ↓
CURATED HUMAN-READABLE REFERENCE
  ↓
TECHNICAL VERIFICATION
  ↓
ALP REDESIGN / ILLUSTRATION
  ↓
DETERMINISTIC OVERLAYS
  ↓
REAL PIXEL REVIEW
```

The governed concept comes from the existing pedagogical chain (assertion family → capability → diagram blueprint, per CC-05D §B) — never invented at the artwork stage. A curated human-readable reference is then sourced before any illustration begins: public-domain historical diagrams, CC0/openly-licensed educational diagrams, standards-based technical references (e.g. IEC 60617 itself), reputable human-authored instructional diagrams, or physical reference photography where useful. **The reference exists for technical/pedagogical grounding, not stylistic copying** — it establishes that the depicted relationship is real and conventional, not that the final artwork must resemble it visually. Technical verification (checking the reference against an independent authoritative source, not merely trusting the first search result) precedes any redesign work, matching the same "independent verification before treating extraction as governed" discipline [`ADR-0002`](adr/ADR-0002-external-source-verification-and-currency.md) already established for factual content. ALP's own illustration is produced only after that grounding exists, with deterministic overlays (§6) added on top where the visual is class A or C, and real pixel review (CC-05D §D/§H, this document's §9) closing the sequence — the same "no self-approval" discipline already governing every visual in production today.

**Implementation (CC-11.5/CC-11.6):** [`tools/visual-production-studio/`](../../tools/visual-production-studio/README.md) (`npm run visuals:studio`) is the manual-assisted production implementation of this workflow -- a local development tool, not learner-facing product functionality. It holds the structured production catalogue, organised by Visual Family (§14) — governed concept, curated reference, immutable facts, creative freedoms, prohibited changes per individual asset — deterministically builds each individual asset's own copyable ASSET-SPECIFIC PROMPT from that data (§15; a family is an organisational grouping only and never reduces prompt granularity), and provides the paste/drop → preview → validate → safe-save → provenance-record mechanics for TECHNICAL VERIFICATION through REAL PIXEL REVIEW once artwork is produced in a separate ChatGPT session. It does not call any image-generation API itself and does not perform ALP REDESIGN / ILLUSTRATION -- a human (Product Owner) remains the actual illustrator/reviewer at every step, exactly as this section requires.

For each reusable visual family, record where practical: primary reference; source; licence/status; what relationship the reference establishes; secondary verification source(s); and which aspects are immutable technical invariants (the facts that must never change regardless of restyling — e.g. "conventional current flows from + to − outside the source" for any circuit reference, or "the thumb points along conventional current direction, fingers curl in the field's direction" for any right-hand-grip-rule reference).

## 4. Reference library as course-factory asset

The curated human-readable reference library is reusable platform infrastructure, not a one-off Unit 202 artefact. Its purpose is so the system never has to ask an LLM to rediscover, from scratch, how to correctly depict recurring concepts every vocational qualification eventually needs: levers, pulleys, gears, circuits, motors, generators, magnetic-field rules, component symbols, measurement arrangements, and their equivalents in future qualifications. Reference provenance and licensing must be retained alongside each entry, with the same discipline the Proprietary-source boundary (`ARCHITECTURE-OVERVIEW.md`) already requires for factual-content references: a reference's presence in the library never by itself grants it a licence to become a production asset if it is proprietary — only openly licensed or properly cleared references may feed a shipped visual.

## 5. Image generation is not technical authority

Generated imagery (from any current or future image-generation tool) may establish finish, style, material impression, anatomy, depth, context and visual polish. **It must never establish**: circuit topology; schematic symbol geometry; mathematical geometry; directional electromagnetism; hand-rule correspondence; exact force/current/field/motion direction; or assessment answer state. Where generated art and governed deterministic geometry disagree, **deterministic geometry wins** — this is not a style preference, it is a correctness rule, and it is recorded as a hard architectural boundary in [`ADR-0004`](adr/ADR-0004-deterministic-authority-over-generated-instructional-imagery.md) because it is exactly the kind of choice that is expensive to reverse if violated (a learner memorising an AI-hallucinated field direction is a genuine harm, not a cosmetic defect).

## 6. Direction-sensitive electromagnetism — locked-skeleton rule

For the right-hand grip rule, Fleming's left-hand (motor) rule, Fleming's right-hand (generator) rule, and any other magnetic field/current/force relationship, the artwork workflow **must begin from a technically authoritative reference construction** (§3) — never from generated imagery or an image model's/illustrator's visual memory of "what a hand-rule diagram typically looks like," which is exactly the failure mode CC-05D §0 already documented once (a structurally valid, correctly-wired diagram that was nonetheless the wrong teaching visual, and — separately, CC-11.3 — a thumb that did not actually communicate current direction). Before any illustration work begins, the following must be locked against the authoritative reference and treated as immutable for that visual family: hand orientation; digit correspondence; current direction; magnetic-field direction; force direction; motion direction; and N/S relationship. Premium illustration is then created *around* that locked skeleton — restyling the hand, the field lines, the motor housing — never redrawing the skeleton itself from artistic impression.

## 7. UK/IEC technical drawing convention

Electrical/electronic schematic symbols must use the governed UK/IEC convention appropriate to UK vocational electrical training — **BS EN 60617 / IEC 60617** is the current project direction (verified via the LO6 discovery workstream during CC-11.3, e.g. the plain-rectangle resistor symbol rather than the US/ANSI zigzag). US/ANSI conventions must not be substituted where they differ. This is mechanically governed today: `VisualSemanticContract.symbolStandard` (`packages/content-schema/src/visual-governance.ts`) carries the enum value `UK_IEC`, and `scripts/visual-governance/check-visual-completeness.ts` fails any REQUIRED component-symbol visual whose contract does not declare it (see CC-05D's own §A for the contract schema this field extends). The same governed symbol is reusable across lessons, questions, worked examples, assessment diagrams, mocks and future courses via the existing `electronics.component_symbol_card` blueprint/`ComponentSymbols.tsx` pattern — one symbol asset, many consumption points, exactly CC-05D §B's traceability model.

## 8. Labels follow pedagogical state, not a blanket "no baked text" default

**Product Owner correction (superseding this section's original absolute framing):** labels are a pedagogical tool, not something premium artwork should default to omitting. Teaching visuals MAY and often SHOULD contain explanatory labels, callouts and short annotations where they materially improve understanding — THUMB = CURRENT / FINGERS = MAGNETIC FIELD on a hand-rule mnemonic, EFFORT / LOAD / FULCRUM on a lever illustration, N / S on a magnet or generator illustration are all genuinely part of the deliverable, not decoration to strip out for visual cleanliness. An aesthetically clean but pedagogically incomplete image is a failed deliverable, exactly like a technically wrong one.

**The governing boundary is ANNOTATION FOLLOWS PEDAGOGICAL STATE**, never a single fixed rule for every image:

- **TEACHING** — explanatory/answer-revealing labels are permitted and often desirable, because the purpose is to teach.
- **ASSESSMENT** — labels must never reveal the specific knowledge/capability currently being assessed (no "CLOCKWISE FIELD" when field direction is the requested answer; no force arrow when force direction is what the learner must determine). Assessment artwork may still carry neutral stimulus labels the question intentionally *gives* the learner rather than asks them to find: A/B/C identifiers, supplied dimensions/values, axes/units, or a fact (e.g. a given pole orientation or current direction) the question states outright.
- **FEEDBACK** (shown after submission) — may reveal the correct answer, explanatory labels, mnemonic imagery, and why a distractor was wrong, exactly like teaching artwork.

`AnnotationPolicy` (`TEACHING_EXPLANATORY | ASSESSMENT_NON_REVEALING | FEEDBACK_EXPLANATORY | NONE`, `tools/visual-production-studio/catalogue.ts`) is the governed field recording which of these states a given premium asset's artwork is produced for — every asset-specific production prompt states explicitly, never implicitly, whether labels for that specific image are REQUIRED, PERMITTED-but-non-revealing, or should be OMITTED entirely (the last case is the one genuine survivor of this section's original default: a deliberate clean base layer for a fully separate deterministic overlay system, used only where an image needs mode-dependent reveal/hide behaviour a baked-in label cannot provide — assessment-state control, localisation, and future correction remain real reasons to prefer a deterministic overlay in that specific case, just never the universal default this section previously stated).

## 9. Teaching / assessment / feedback states

Visual families should support state-aware presentation exactly as CC-05D §H and §K already govern for class-A visuals, extended here to classes B and C: TEACHING may reveal labels, directions, highlighted paths and explanatory overlays; ASSESSMENT must remove answer-bearing information while preserving fair context; FEEDBACK may reveal the correct governed relationship. Do not create unrelated visual assets for each state — one governed visual skeleton (the class-B/C illustrated base) should support all three states via deterministic overlay presence/absence, exactly the pattern `DiagramRevealProps` already establishes for class-A diagrams (`apps/mobile/src/components/diagrams/DiagramRenderer.tsx`).

## 10. Premium quality standard

The target is a category-leading paid consumer learning product (Product Principle 24: "narrow commercial quality beats broad rough coverage"). A visual is not finished merely because it is technically valid, rendered, and mechanically governed — production approval requires all five of: **technical correctness** + **pedagogical clarity** + **mobile legibility** + **visual quality** + **consistency with ALP's visual language**. Real pixel-level review remains required for every one of these five, not only the first — automated/mock semantic checks (CC-05D §F/§N's explicit "informational only" framing) do not, on their own, constitute visual approval, and neither does a class-A mechanical governance pass on its own constitute approval of a class B/C visual's illustration quality (mechanical governance can prove a deterministic overlay is present and correct; it cannot judge whether the illustrated layer around it looks premium).

## 11. Art direction / style system

ALP will maintain an instructional-visual style guide ("illustration bible") governing: visual personality; line hierarchy; semantic colour roles; arrow/motion grammar; physical-object simplification; perspective; dark-theme behaviour; mobile composition; technical-overlay rules; teaching/assessment states; accessibility; and consistency across future qualifications. The target character: premium, contemporary, technically credible, mature enough for adult learners, approachable to apprentices — explicitly **not** childish, **not** generic corporate vector art, and **not** textbook-only line art where a physical concept genuinely deserves illustration. The style guide itself is not built by this document; this document records that it is required and what it must govern, matching CC-05D's own established pattern of recording an architectural requirement before the implementation package that fulfils it exists (e.g. CC-05D §1's explicitly out-of-scope items, later closed by CC-11/CC-11.3).

One durable, already-governed fact the future style guide must build on rather than replace: every current class-A diagram uses the app's real dark-theme design tokens (`apps/mobile/src/lib/tokens.ts` — background `#0B0D12`, text `#F2F4F8`, secondary text `#9AA3B2`), confirmed correct during CC-11.3's real pixel review (the actual defect found there was in the review-tooling's own mockup background, not in the diagrams — see `PROJECT-STATUS.md` §CC-11.3 item 4). Dark-theme behaviour for premium illustration (classes B/C) must be specified against these same tokens, not a separately invented palette.

**Default premium surface (Product Owner correction): soft dark slate/blue-grey, not pure black.** Class-A diagrams sit on the app's own `#0B0D12` UI background directly, which is correct and unchanged. Premium illustrated artwork (class B, and class B's illustrated layer within class C) is a different surface — its own composed background, not the app chrome — and defaults instead to a **muted, medium-dark slate/blue-grey with a subtle smooth gradient**: visibly softer and cooler than a flat black void, while remaining dark enough for a premium technical aesthetic and strong contrast against white text and ALP's governed semantic colours (conventional current: vivid cool blue; magnetic field: green/turquoise; force/mechanical emphasis: warm yellow-orange where governed; motion: cyan/blue-green where governed; heat: orange-red; warning/error: controlled red). No strong texture, decorative scenery, harsh vignette, or neon/cyberpunk treatment; no isolated black rectangle that would look pasted onto a softer interface. The target character throughout is **industrial precision + premium consumer learning product** — not harsh black/gamer UI, not neon cyberpunk, not children's educational software, not corporate e-learning, not a white textbook diagram, not heavy industrial grunge, not power-tool advertising.

This is a **default, not an absolute rule** — an individual asset may depart from it where pedagogically or visually justified (`VisualAsset.backgroundStyleOverride`, `tools/visual-production-studio/catalogue.ts`), and it never applies to class-A deterministic schematics, graphs, symbols, or assessment tiles, which have no illustrated background of their own to style. When several premium assets belong to the same visual family (§14), their background character should stay consistent with each other so the set reads as one coherent teaching family, unless a deliberate pedagogical reason requires a change. Background styling is never technical authority (§5) — it must never cause a change to geometry, hand orientation, topology, arrow direction, or any governed-meaning label.

## 12. Visual completeness must be demand-driven

Do not validate only "every existing visual has a renderer." Visual completeness must be assessed from lesson / capability / misconception / instructional need → required visual → governed asset → renderer → semantic contract → lesson integration, in that direction — never the reverse ("we have this asset, where can we use it"). A missing visual must not be invisible merely because no blueprint was ever created for it. This principle is now mechanically enforced for class-A visuals by `scripts/visual-governance/check-visual-completeness.ts` (`npm run visuals:completeness:check`, built in CC-11.3, walking every current lesson step's declared visual need and verifying the asset/renderer/contract/symbol-convention chain exists) — the same demand-driven gate applies conceptually to classes B/C once they exist, extended to also verify illustration-production status (referenced, not yet illustrated, illustrated-pending-review, approved) rather than only renderer/contract presence.

**Restated explicitly, because both wrong framings are tempting shortcuts:** visual completeness is **not** "every lesson has an image," and it is **not** "every concept has N images." Visual completeness means: for each governed teaching need, the learner is provided with the minimum set of technically correct, pedagogically useful visual states required to understand, practise and transfer the concept — which may be no image, one image, or several (§14's Visual Family model is the mechanism this resolves through). A lesson with zero visuals can be completely correct; a lesson with five can still be missing the one that actually matters.

## 14. Visual families — variable-size, demand-driven (never a fixed template)

**Core architectural rule: VISUAL COUNT FOLLOWS PEDAGOGICAL NEED.** A governed instructional concept is never modelled as requiring a fixed number of images. The correct abstraction is a **Visual Family**: the complete governed set of visual assets needed to teach, practise, assess and explain one concept effectively. A family may contain zero premium illustrations, one, two related ones, several sequential/configuration/state illustrations, one or more deterministic technical diagrams, or a combination — decided individually per concept, never templated as "one image per concept" or "two images per concept."

To determine a family's actual asset count, ask: (1) what must the learner *see* to understand the concept; (2) what configurations/states must be compared; (3) what memory aid, if any, is useful; (4) what should disappear during assessment; (5) what should be revealed during feedback — then define the smallest family that teaches the concept completely without unnecessary duplication. Manufacturing extra artwork merely to satisfy a family structure, or forcing a genuinely multi-state concept into one overcrowded image, are both violations of this rule.

**Roles a family's assets may play** (`VisualAssetRole`, `tools/visual-production-studio/catalogue.ts`): `PHENOMENON`, `MNEMONIC`, `CONFIGURATION`, `SEQUENCE_STATE`, `COMPARISON`, `PHYSICAL_RECOGNITION`, `TECHNICAL_DIAGRAM`, `ASSESSMENT_SUPPORT`, `FEEDBACK_SUPPORT` — a family is never required to use every role, and never required to reach a fixed cardinality.

**Worked examples from the live Unit 202 catalogue (CC-11.6 restructuring, 20 families / 29 assets):**

- **Right-hand grip rule** (`unit202.family.right-hand-grip`) — two assets: the electromagnetic *phenomenon* (a field genuinely circulates around any current-carrying conductor) and the *mnemonic* used to predict its direction, kept distinct so a learner cannot memorise the hand gesture without understanding what it predicts. A third conceptual role, assessment support (a deterministic technical stimulus with no hand), already exists as the separately-governed CC-05D deterministic diagram — not duplicated here as a third premium asset. The same phenomenon+mnemonic pattern was applied, by direct analogy, to Fleming's left-hand rule (motor effect) and Fleming's right-hand rule (generator effect).
- **Levers** (`unit202.family.levers`) — three CONFIGURATION assets (Class I/II/III), each a clean, unambiguous illustration, rather than one image forcing all three arrangements together and blurring the distinction the learner must recognise.
- **Pulleys** (`unit202.family.pulleys`) — exactly two CONFIGURATION assets (fixed; movable), a count *confirmed by governed evidence*, not assumed. Before finalising this family, the actual Unit 202 corpus (`FP-CONCEPT-PULLEY-001`, `FP-PULLEY-FIXED-VS-MOVABLE-001`, `FP-REL-PULLEY-MECHANICAL-ADVANTAGE-001`, `FP-REL-PULLEY-FORCE-DISTANCE-TRADEOFF-001`, `cap.foundational.pulleys.recognise`) was reviewed in full: it teaches fixed-vs-movable and the qualitative more/fewer-supporting-segments relationship, never a specific two-/three-pulley or block-and-tackle configuration, and multiple governed artefacts (the existing visual-semantic-contract's `mustNotShow`, `PulleyDiagram.tsx`'s own header comment) explicitly declare multi-pulley complexity out of scope. No third pulley asset was added — doing so would have manufactured syllabus content the corpus never actually governed.
- **Simple, single-concept families** (12 of the 20) — a series circuit, a parallel circuit, driver/driven gears, an AC sine waveform, and others each remain exactly one asset, because the concept is genuinely simple and one clear image is sufficient. No family is expanded merely because the tooling now supports more than one asset.

**Where the governed corpus does not clearly establish that a specific candidate configuration is required teaching content**, the correct outcome is to record the asset as needing an explicit Product Owner/Architect scope decision (`VisualAsset.needsScopeConfirmation`) rather than inventing syllabus content — the pulleys family above needed this check and resolved cleanly to "no third asset"; a future family that genuinely cannot resolve from existing evidence should use this mechanism instead of guessing either way.

**A family is an organisational grouping only — it never reduces prompt granularity.** Every individual asset, even one nested inside a four-asset family, gets its own fully independent, deterministically-generated ASSET-SPECIFIC PROMPT (§15) and its own copy/paste/approve controls in the Studio. Grouping only changes how assets are *displayed* together (so visually related images can be produced consistently and reviewed together); it never merges two required images into one prompt, and it never means a Product Owner has to manually edit a generic family-level prompt into an asset-specific one.

## 15. Studio prompt architecture — exactly two prompt layers, one prompt per asset

The Visual Production Studio exposes exactly two prompt layers, never more:

- **PROMPT 1 — MASTER ART SESSION PROMPT**, used once at the start of a fresh ChatGPT art session. Establishes ALP's visual identity, the reference-first rule, the technical-correctness hierarchy, mobile/dark-theme quality, the labels-follow-pedagogical-state rule (§8), visual-family awareness without assuming every concept needs multiple images, and the assessment-artwork restriction.
- **PROMPT 2 — ASSET-SPECIFIC PROMPT**, used once *per individual asset* — including every individual asset within a multi-asset family. A four-asset family exposes four separate, individually copyable prompts, never one generic family prompt the Product Owner must hand-edit. Each asset-specific prompt states: the family name/id and this asset's role and position within it (for context and cross-family visual consistency only, never to imply the other family members must also be produced); the exact instructional purpose of *this* asset; primary/secondary references; immutable technical facts; the annotation instruction for this specific asset (§8); creative freedoms; prohibited changes; deterministic responsibilities outside the artwork; the exact requested deliverable; an explicit "Produce ONLY this asset — do not automatically create the other members of the visual family" instruction; and the critical direction-verification rule (never trust a caption's own claim of geometric correctness — inspect the actual arrowheads/geometry against the reference).

The Studio therefore tracks three distinct counts, never conflated: **visual family count** (an organisational grouping), **individual asset count** (every genuinely distinct required image), and **promptable artwork asset count** (individual assets minus any still blocked on a reference, still pending a scope decision, or explicitly marked as having no image-generation deliverable at all — e.g. the governed UK/IEC symbol system, produced deterministically by `ComponentSymbols.tsx`, never an art session). Only promptable artwork assets are offered a real ChatGPT prompt; every promptable artwork asset has its own.

## 16. Relationship to CC-05D

This document adds no new field to `VisualSemanticContract` beyond what CC-11.3 already added (`symbolStandard`, §7 above) and changes no CC-05D mechanical/semantic QA behaviour. CC-05D remains the sole authority for *how a visual is validated once it exists* (contracts, canonical variants, mechanical checks, two-pass semantic QA, human-review escalation, publication gating). This document is the sole authority for *how a visual is produced before it reaches that pipeline*. A future class-B/C visual still needs a `VisualSemanticContract`, still needs canonical variants for its deterministic overlay elements, and still needs to pass every CC-05D gate — premium production status is an additional property recorded alongside, never a substitute for, CC-05D governance.

## 17. Comprehensive audit and the three-level hierarchy (CC-11.7)

The 66 pre-existing CC-05D canonical variants were always **a baseline to reconcile, never the target visual count**. CC-11.7 performed a full corpus audit (every Unit 202 lesson, assertion, capability, formula family and question blueprint — not only the visuals already built) and reconciled every one of those 66 variants into a third, more granular hierarchy level the Studio catalogue now models explicitly:

```text
VISUAL FAMILY
  ↓
PRODUCTION / BASE ASSET
  ↓
CANONICAL LEARNER-VISIBLE STATE
```

A **production/base asset** is a reusable premium or deterministic visual object; a **canonical learner-visible state** (`CanonicalState`, `tools/visual-production-studio/catalogue.ts`) is one distinct presentation a learner may actually encounter (in `TEACHING`, `PRACTICE`, `ASSESSMENT`, `FEEDBACK`, or `MULTI_STATE` where a state is genuinely shared unchanged across contexts). A single base asset routinely supports several states — e.g. one illustrated motor-effect base asset carries all 8 pole/current/mode combinations the deterministic overlay system already governs — and states are never collapsed merely because they share a base. `AnnotationPolicy`/required-labels now apply **per state**, not only per asset, since the same base asset's teaching and assessment states genuinely need different label treatment (§8).

**Reconciliation result: zero existing canonical variants silently lost.** Every one of the 66 was mechanically re-derived from the real `CANONICAL_VARIANT_BUILDERS` output and matched 1:1 against a `CanonicalState.existingCanonicalVariantId` in the Studio catalogue — verified by direct diff (0 missing, 0 extra) and enforced going forward by `tools/visual-production-studio/audit.ts` (`npm run visuals:studio:audit`), which fails the build if a future edit silently drops one.

**The audit found genuinely new REQUIRED visual needs beyond the 66** — none invented from a prior session's own worked examples, each independently corroborated by a named misconception or an existing `QuestionBlueprint` with no visual representation: a diode forward/reverse-bias current-direction diagram, rectifier/inverter output-waveform shapes (distinct from the plain sine wave), and a capacitor RC charge/discharge transient curve. See [`reports/instructional-visuals/unit202-comprehensive-visual-audit.md`](../../reports/instructional-visuals/unit202-comprehensive-visual-audit.md) for the full audit, including every USEFUL finding deliberately tracked but not yet catalogued (to avoid inflating the catalogue with decorative imagery, per §12's demand-driven principle) and every concept explicitly confirmed NOT_NEEDED. ## 18. Materialising the USEFUL queue and one-art-prompt-per-image-job (CC-11.7A)

CC-11.7 deliberately tracked 10 USEFUL findings (§12/§17) without giving them a live catalogue presence, to avoid inflating the catalogue with decorative imagery. That left a real gap for the Studio's intended purpose as the *complete* Unit 202 visual production queue, not merely the minimum-REQUIRED one: a Product Owner opening the Studio had no way to see, prioritise, or track those 10 findings at all. CC-11.7A closes that gap without re-auditing Unit 202 and without upgrading any of the 10 to REQUIRED.

**All 10 are now live catalogue assets.** Each carries `needOverride: "USEFUL"` (`tools/visual-production-studio/catalogue.ts`) — a distinct, permanent field kept deliberately separate from `VisualNeedClassification`'s REQUIRED-by-default derivation, so a materialised USEFUL asset never silently becomes REQUIRED merely because it is now visible in the Studio. `dashboard.ts` tracks `required`/`useful` (and their art-job/approved/outstanding sub-counts) as fully independent buckets throughout — REQUIRED completeness can never appear incomplete because of USEFUL production status, or vice versa. `audit.ts`'s `EXPECTED_USEFUL_FINDING_ASSET_IDS` gate fails the build if any of the 10 is ever silently dropped again. 8 of the 10 are currently `BLOCKED_REFERENCE` (no individually-sourced reference approved yet) — tracked honestly, never fabricated, never removed for lacking one.

**ONE ART PROMPT PER DISTINCT IMAGE JOB, made structural.** The pre-existing `unit202.components.physical` asset carried 6 `CanonicalState`s for 6 genuinely different physical objects (resistor, capacitor, diode, LED, thermistor, transistor) behind one prompt, one filename, one approval slot — a real granularity defect, not a stylistic preference. Split into 6 independent `ProductionAsset`s, each with its own prompt/filename/save-slot/approval state; REQUIRED classification and reference readiness were left exactly as previously accepted, only the structural granularity changed. `validateCatalogue()` now mechanically enforces this going forward: a `PHYSICAL_RECOGNITION`-role asset may never carry more than one `CanonicalState`. The 5 specialist USEFUL physical-recognition findings (zener diode, photodiode, DIAC, TRIAC, thyristor/SCR) were built directly in this corrected shape.

**Updated counts**: 20 → 21 families (+1, `unit202.family.current-direction`), 32 → 47 production assets (+15: +5 from the physical-component split, +10 materialised USEFUL), 87 → 98 canonical states, 28 → 33 REQUIRED assets. CC-11.7B is the final pre-production audit: it does not re-derive REQUIRED/USEFUL needs, but asks whether the 98 canonical states CC-11.7/CC-11.7A produced were compressed into the *correct* number of actual production images -- a `CanonicalState` is never automatically a separate image, and a `ProductionAsset` supporting several states is never automatically valid merely because it is technically possible.

## 20. Automated production pipeline and the Gemini two-asset proof (CC-11.8)

CC-11.7B/C established a fully accounted, correctly-blocked production queue but every job still required a human to run ChatGPT manually through the Studio's copy/paste workflow. CC-11.8 locks the **canonical automated operating model** -- who/what does what -- and proves the render step of it end-to-end with two real generated assets.

### 20.1 Division of responsibility

| Role | Responsibility |
|---|---|
| **Claude / Claude Code** | Determines what visuals are required from the governed corpus; creates and maintains visual asset contracts (`catalogue.ts`); classifies production method; orchestrates the pipeline; downloads/caches APPROVED references from the governed reference catalogue; sends reference + prompt + style information to Gemini; saves masters and production derivatives with full provenance; performs an independent technical/pedagogical audit of the actual generated pixels (never trusts a caption); performs bounded automatic retries (max one per asset); produces the human-readable review pack; **never silently promotes an uncertain image to Product Owner review as if it were confidently correct.** |
| **ChatGPT / Product Owner (reference-research stage)** | Researches suitable technical/pedagogical reference images; verifies a proposed reference actually supports the required geometry/topology; records provenance/licence/suitability; a reference is APPROVED at this stage before it may enter generative production. |
| **Gemini** | Implementation renderer only. Receives the actual approved reference-image file (never merely a URL), the individual asset's production contract, and the canonical ALP visual style specification (`docs/design/ALP-INSTRUCTIONAL-VISUAL-STYLE-GUIDE.md`). Redraws/re-illustrates the governed asset. **Is never technical authority** -- unchanged from ADR-0004. |
| **Product Owner** | Receives the final human-readable visual review pack; remains final approval authority. |

**Governance rule (hard, no exception process short of a superseding ADR):** no generative asset may enter production without an approved technical/pedagogical reference when that asset requires reference-locked geometry. Claude may identify that a reference is missing; Claude must not independently select an arbitrary replacement reference and continue generation -- an asset with no approved reference stays `BLOCKED_REFERENCE` (§19) until the reference-research stage approves one.

### 20.2 Production path

```text
GOVERNED CORPUS
  -> VISUAL-NEED DETERMINATION            (visualNeedClassificationFor -- §17)
  -> VISUAL ASSET CONTRACT                (catalogue.ts VisualAsset)
  -> REFERENCE_REQUIRED?
  -> APPROVED REFERENCE CATALOGUE         (ChatGPT/PO reference-research stage)
  -> LOCAL REFERENCE ACQUISITION          (tools/visual-production-studio/reference-acquisition.ts)
  -> REFERENCE VALIDATION                 (real image/SVG bytes, not an HTML error page; SHA-256 recorded)
  -> GEMINI REFERENCE-DRIVEN REDRAW       (tools/visual-production-studio/gemini-client.ts)
  -> AUTOMATED INDEPENDENT AUDIT          (Claude inspects the actual candidate pixels against immutable facts)
  -> BOUNDED CORRECTION                   (max one automatic retry)
  -> HUMAN-READABLE REVIEW PACK           (generate-visual-proof-review.ts)
  -> PRODUCT OWNER APPROVAL
  -> MASTER ASSET
  -> OPTIMISED PRODUCTION DERIVATIVE
  -> CONTENT RELEASE
```

Standing rules this path enforces, unchanged from earlier sections and ADR-0004:

- assessment visuals default to deterministic production (§8/§17/§19) -- generative imagery never defines assessment answer geometry;
- exact geometry and directional relationships remain deterministic overlay, never a generative claim (§3 of the style guide; ADR-0004 §Decision);
- generated imagery is never authority -- deterministic geometry wins on any disagreement (ADR-0004, unchanged);
- Product Owner approval remains the final gate; nothing in this automated path writes to the governed manifest or the shipped app asset tree on Claude's own authority.

### 20.3 Two-asset proof

Proved end-to-end on two already-`READY` (genuinely reference-locked, per the CC-11.7C correction) assets: `unit202.magnet.field` (a straightforward physical/conceptual subject) and `unit202.pulleys.fixed` (a technically constrained subject -- fixed anchor, direction-change-only rope path). Each: real reference file acquired and hashed, generated via `gemini-3.1-flash-image` with the reference image supplied as actual bytes (never a URL), independently audited by Claude against the asset's immutable facts, saved as a versioned master + mobile derivative under `reports/instructional-visuals/premium-artwork/proof/` (a review/audit-trail location, deliberately not the shipped `apps/mobile/src/assets/...` tree or the approved-artwork manifest -- these are unapproved candidates pending Product Owner review, not production assets). Full results: `reports/instructional-visuals/unit202-visual-production-proof-review.pdf` and `PROJECT-STATUS.md` §CC-11.8.

This proof establishes the pipeline mechanism only. It does not constitute Product Owner approval of either candidate image, and it does not process the remaining Unit 202 art-job queue -- see §19's dashboard/blocked-reference accounting for the real remaining workload.

## 21. CC-11.9: external reference handover, white/light style, reusable canonical assets

**External reference handover as implementation authority.** A Product Owner-supplied external reference-research handover (`reports/instructional-visuals/reference-research/unit202/`) is the reference-decision authority for the assets it covers -- Claude does not independently re-research or substitute references it names. Its per-asset recommendations (`unit202-reference-implementation-checklist.json`, the actual data used) are applied to the live catalogue via an **additive overlay**, `tools/visual-production-studio/reference-corrections.ts`, rather than an in-place rewrite of `catalogue.ts`'s own asset declarations -- several asset families there (`motor.effect.*`, `generator.*`, `magnet.poles.*`, `gears.*`, `components.physical.*`, `diode.bias-direction.*`) are generated programmatically from shared loop/template data tables, not one hand-written block per assetId, and an automated text-block rewrite against those templates proved unsafe. Any code that needs an asset's real reference or true readiness must call `effectivePrimaryReference()`/`effectiveSecondaryReference()`/`effectiveReferenceReadiness()`, never `asset.primaryReference` directly.

**Reference preparation.** Composite sources (a reference file containing more geometry than one asset should depict) are cropped/isolated, PDF pages are extracted (via the system `pdftoppm`/Poppler binary, not a new npm dependency), and multi-source comparisons are composed into one plain reference sheet -- all via `tools/visual-production-studio/reference-preparation.ts`, using the same "Playwright screenshots things" technique already used for SVG rasterisation. Prepared references are deliberately boring and technically clear, never learner-facing artwork.

**Zero-missing-reference gate.** Before any production run, every generative (non-`DETERMINISTIC_TECHNICAL`) asset must resolve to a real local reference input -- `tools/visual-production-studio/generate-reference-readiness-final.ts` proves this mechanically (missing references / unresolved placeholders / unprepared composites, each must be exactly zero) and writes `reports/instructional-visuals/unit202-reference-readiness-final.{json,md}`.

**Background direction: white/near-white, not dark slate.** The style guide's background default changed (see `ALP-INSTRUCTIONAL-VISUAL-STYLE-GUIDE.md` §2) -- both `prompt-builder.ts`'s `DEFAULT_BACKGROUND_INSTRUCTION` and the Gemini-proof prompt builder (which reads the style guide live, so it inherits the change automatically) reflect this.

**Required technical semantics are part of acceptance, not deferred.** `prompt-builder-gemini.ts`'s clean-base-art default is corrected: an asset's own `requiredLabels` are now stated explicitly in the generation prompt and required to be present *and correct* in the generated image (see ADR-0004's Consequences update). `forceCleanBaseArt` is used only for an asset whose `deterministicOverlayResponsibilities` genuinely cover every label it needs.

**Instructional visuals are reusable platform assets.** A commissioning course (e.g. Unit 202) is not the permanent owner of a generated visual -- see `ALP-INSTRUCTIONAL-VISUAL-STYLE-GUIDE.md` §8. Conceptually: `CanonicalVisualAsset -> approved master/state/version -> UsageBinding(s)` (qualification, course, unit, lesson, pedagogical role, teaching/assessment/remediation context). Technical approval (reference provenance, immutable facts, audit result) travels with the canonical asset and is reusable across compatible future `UsageBinding`s; pedagogical suitability is still checked per new binding, never assumed. This is recorded here as a data-model intent for future course-factory packages (`reference-corrections.ts`'s header comment carries the same note) -- existing Unit-202-prefixed `assetId`s are not renamed to implement it now.

**Production run tooling.** `tools/visual-production-studio/visual-proof/run-production.ts` supersedes the narrower `run-proof.ts` (which remains, unmodified, as the historical record of the original 2-asset CC-11.8 proof) -- it resolves references through the correction overlay, accepts an optional prepared-reference override, and applies the corrected label policy. `generate-pilot-review.ts` produces the four-asset pilot review pack (`reports/instructional-visuals/unit202-four-asset-pilot-review.{pdf,json}`).

## 22. CC-11.12: semantic reference QA as a hard pre-generation gate

**Reference-first was necessary but not sufficient.** §21's zero-missing-reference gate proves a reference *exists* for every generative asset; it never proved the exact frame supplied to the model was *semantically fit for the exact governed state*. Product Owner / ChatGPT semantic review of all 51 CC-11.9–CC-11.11 generative outputs found 22 that had passed the prior single-verdict automated audit but were, on inspection, reference-input failures: a composite reference leaking sibling content into the output, a direction-sensitive state re-derived instead of preserved from a locked reference, an acquired reference never actually shown in review (`reference preview not found`) while its output drifted, a reference's notation conflicting with the course's own governed notation, and a wrong-composition-authority reference type for the governed teaching level. Full decision record: `ALP-INSTRUCTIONAL-VISUAL-STYLE-GUIDE.md` §9, `reports/instructional-visuals/reference-research/unit202/semantic-qa-cc11.12/VISUAL-REFERENCE-SEMANTIC-QA-PRODUCT-DECISION.md`, and ADR-0004's CC-11.12 update. **This decision is permanent product/content governance, not a Unit-202-only fix — it applies to every future module, course and qualification.**

**Semantic-QA fields on the reference model.** `tools/visual-production-studio/semantic-reference-qa.ts` -- a sibling additive overlay to `reference-corrections.ts`, keyed the same way -- exports `SEMANTIC_QA`, one record per reviewed state: `semanticQaStatus`, `exactLearnerVisiblePurpose`, `keepElements`, `cropRemoveElements`, `requiredFinalElements`, `prohibitedFinalElements`, `modelMustNotInfer`, `familyConsistencyRequirements`, `assessmentLeakageConstraints`, `ambiguityRisk`, `referenceDisposition`. `referenceDisposition` is one of `APPROVED_DIRECT` / `APPROVED_PREPARED` / `REPLACE_REFERENCE` / `REJECT_REFERENCE`; `run-production.ts` refuses to generate for a state whose disposition is not one of the first two.

**Three independent audit verdicts.** `ProofAuditResult` is extended with `technicalVerdict`, `pedagogicalClarityVerdict`, `visualProductQualityVerdict` (each `PASS` / `FAIL` / `UNCERTAIN`), plus the existing overall `verdict`. Overall PASS requires all three PASS; an `UNCERTAIN` on any dimension blocks an automatic overall PASS, same as a FAIL. This replaces the single-dimension "did the geometry look right" verdict used through CC-11.11 — a technically correct image that is pedagogically confusing (competing/duplicated cues) or visually sub-premium (fuzzy, low-legibility) was previously indistinguishable from a genuinely good one.

**Review-package rule.** A reference-driven asset's review page must show the actual prepared reference frame; `reference preview not found` is now a hard review failure, not a cosmetic gap, per the Product Decision's own explicit rule.

## 23. CC-11.13: pipeline hardening -- production modes, asset lifecycle, and reference-as-authority-not-final-asset

**Post-Unit-202 correction package, driven by a Product Owner decision that is permanent, platform-wide governance, not a Unit-202-only fix.** CC-11.12 established that the exact reference frame must pass semantic QA before generation; it did not yet stop the pipeline from (a) treating a vectorised/traced reference as an acceptable final asset, (b) defaulting to 3D/photoreal treatment for diagrams that are clearer flat, (c) reporting PASS on a "correction" that quietly removed a previously-approved element, or (d) conflating "technically correct" with "finished" with "Product Owner approved". This package closes those four gaps without regenerating any imagery.

**Reference-as-authority, not reference-as-final-asset.** A technically suitable reference defines geometry/direction/topology; the shipped ALP asset is normally an **original redraw** grounded on that authority, never a lifted/traced/vectorised copy of the reference itself, and never a free re-interpretation that drifts from the technical relationships the reference establishes. See the style guide §10 for the full rule and `NO_GENERATIVE_INFERENCE_RELATIONSHIPS` in `tools/visual-production-studio/production-mode.ts` for the platform-wide list of relationships (right-hand-grip field rotation, Fleming correspondences, motor/generator current-field-force-motion, motional-EMF B/l/v geometry, lever-class ordering, circuit topology, diode polarity, electrolysis ion direction, IEC symbol geometry, switching-symbol geometry) that must never be left to generative inference under any production mode.

**2D-diagrammatic default, not 3D.** Teaching diagrams default to clean, flat, 2D/diagrammatic treatment; perspective/3D is opt-in only where it materially improves comprehension of a genuinely spatial relationship. See style guide §10.

**Governed production-mode model.** `tools/visual-production-studio/production-mode.ts` records, per asset (or per-state for the 3 direction-sensitive assets), one of five modes:
1. `DETERMINISTIC_TECHNICAL` -- exact technical/vector content only, 1:1 with catalogue.ts's own `productionClass`.
2. `ORIGINAL_REDRAW_FROM_REFERENCE` -- the default for most teaching diagrams: a clean original ALP redraw grounded on a clear reference, no technical reinterpretation.
3. `HYBRID_REDRAW_PLUS_DETERMINISTIC_OVERLAY` -- an original redrawn base plus a deterministic overlay for a genuinely overlay-appropriate state-varying fact (a dimension/comparison callout) -- never used to defer a directional/topological fact that belongs baked into the image itself.
4. `GENERATIVE_CONCEPTUAL` -- original/conceptual generation where no single reference's exact relationships must be preserved.
5. `DEFERRED_POLISH` -- not a creation method; a status meaning correct/usable now, final polish intentionally postponed.

Generation via an image model is a production **option** selected per asset via this model, never a mandatory step for every asset. All 53 Unit 202 ProductionAssets are classified; see the file for the full mapping and rationale.

**Asset-lifecycle gating, separating correctness from appearance from approval.** `tools/visual-production-studio/asset-lifecycle.ts` adds seven gates -- `REFERENCE_APPROVED` -> `SEMANTIC_COMPOSITION_APPROVED` -> `TECHNICAL_MASTER_APPROVED` -> `PEDAGOGICAL_MASTER_APPROVED` -> `POLISH_PENDING` -> `POLISHED` -> `PRODUCT_OWNER_APPROVED`. Key rule: an asset may be development-usable while still `POLISH_PENDING` (full polish is never a precondition for internal product-development use) -- but an asset with a known technical/pedagogical teaching error is never treated as approved merely because it looks acceptable; `isDevelopmentUsable()` checks debt classification first, before any polish/approval state.

**PRESERVE / ADD / REMOVE / REPLACE remediation contract.** `asset-lifecycle.ts`'s `RemediationContract` type makes preserve-lists first-class for every future remediation package: `{ preserve, add, remove, replace }`. This directly prevents the failure class named by this package's own brief -- deleting a previously-useful approved element (e.g. a correct symbol) when the actual instruction was only to add a missing companion elsewhere. `preserve` is never optional; an empty preserve list is a deliberate full-redraw choice, not a default.

**Unit 202 visual-debt register.** `tools/visual-production-studio/generate-visual-debt-register.ts` -> `reports/instructional-visuals/unit202-visual-debt-register.{json,md}`, classifying every asset with a known debt finding into `BLOCKING_CORRECTNESS` (3: `unit202.right-hand-grip.teaching`'s field-rotation cue, `unit202.emf.motional` pending one more confirmation pass, `unit202.levers.class-3`'s pedagogically-worse-than-reference redraw), `DEVELOPMENT_USABLE_POLISH_PENDING` (1: `unit202.electrolysis`'s duplicated label), and `DEFERRED_SCOPE` (1: `unit202.components.physical.resistor`'s deterministic colour-band overlay). Deliberately lean -- the remaining 46 of 51 generative outputs carry no individually-identified debt and are not padded into the register merely to look thorough.

**No broad regeneration in this package.** Two specific known-blocking assets (`unit202.right-hand-grip.teaching`, `unit202.levers.class-3`) are recorded as targeted future bounded-fix candidates, not generated now -- see PROJECT-STATUS.md §CC-11.13's "next package" recommendation.

## 24. CC-11.13A: state-record corrections (data/status only, CC-11.13's architecture unchanged)

**A pure metadata correction, not an architecture change.** CC-11.13A fixed four state-record errors CC-11.13 itself introduced while establishing the (still-correct, unchanged) production-mode and lifecycle architecture:

1. **Lifecycle-gate contradiction fixed.** `unit202.right-hand-grip.teaching` and `unit202.emf.motional` had both been left at a gate (`TECHNICAL_MASTER_APPROVED` / `PEDAGOGICAL_MASTER_APPROVED`) that asserts a passed technical audit, while both are also `BLOCKING_CORRECTNESS` for a genuine technical defect -- a live contradiction (a technical error cannot coexist with "technical master approved"). Both corrected to `SEMANTIC_COMPOSITION_APPROVED` (the prepared reference/frame is locked and correct; the generated master built from it is not).
2. **Motional-EMF's next fix scope corrected.** A second technical defect was found in the CC-11.12-corrected board: `l` is placed along the wrong geometric dimension. The governed relationship for the next fix, now recorded explicitly in `NO_GENERATIVE_INFERENCE_RELATIONSHIPS`: `l` = active conductor length, `v` perpendicular to `l`, `B` perpendicular to both. `unit202.emf.motional` is added back into the three-asset next bounded-fix scope (§CC-11.13's own recommendation had accidentally dropped it, listing only right-hand-grip and Class III lever).
3. **Component-family direction corrected.** CC-11.12's removal of `unit202.components.physical.capacitor`'s baked UK/IEC symbol "for family consistency" was the wrong direction. The correct, now-recorded rule: PHYSICAL COMPONENT RECOGNITION IMAGE + DETERMINISTIC UK/IEC SYMBOL COMPANION, for every component including the capacitor -- the fix should have added a deterministic symbol companion to the *other* components, never removed the capacitor's. Not corrected now (Unit 202 component cleanup remains deferred); recorded in `production-mode.ts` and a new `DEFERRED_SCOPE` `asset-lifecycle.ts` entry so a future course-production package implements the rule correctly from the start.
4. **Suite-level polish status added.** `asset-lifecycle.ts` now exports `UNIT202_GENERATIVE_SUITE_STATUS` (`UNIT202_GENERATIVE_SUITE` / `GLOBAL_POLISH_PENDING`), covering the 46 of 51 generative outputs with no individually-identified defect. CC-11.13's visual-debt register had implied these were visually finished merely because no individual defect was recorded; Product Owner review found the suite as a whole reads generally below the desired finish (sharpness, line quality, consistent labelling, family consistency, generative softness, ALP style normalisation). This status is explicitly not a development blocker and explicitly not Product Owner approval -- a controlled polish pass is recorded as needed, after the `BLOCKING_CORRECTNESS` items are closed.

**Zero image-generation calls.** This package is a data/status correction only -- the production-mode architecture, original-redraw principle, 2D-diagrammatic default, semantic reference QA, no-generative-inference rules, remediation contract and general lifecycle architecture are all unchanged. See `reports/instructional-visuals/unit202-visual-debt-register.md` for the corrected register and PROJECT-STATUS.md §CC-11.13A.
